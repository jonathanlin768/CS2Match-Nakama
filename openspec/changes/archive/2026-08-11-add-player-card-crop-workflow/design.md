## Context

项目目前只在 `#Player.xlsx` 中保存 `portrait`，编辑器也只提供单图上传和预览。实际素材是一张完整的 `2:3` 选手卡面，而比赛阵容需要从同一张图中展示更紧凑的 `5:7` 头像。若策划手工维护完整卡面和头像两份图片，重新构图、替换素材或调整头像时很容易失配，也无法从数据表还原裁切意图。

本变更贯穿四个已有能力边界：配置工作台负责素材入库和裁切编辑，Luban/Go 结构负责数据传递，TutorialPage 展示完整卡面，BattlePage 根据比赛快照动态还原裁切头像。裁切参数是静态展示数据，不参与战斗数值和事件推演。

现有样例卡面均为 `1024x1536` PNG，即 `2:3`。实现仍以图片自然尺寸为准，不把该分辨率写死，以便后续接纳其他分辨率的 `2:3` 素材。

## Goals / Non-Goals

**Goals**

- 在 Player 专属编辑页上传、预览完整卡面，并使用固定 `5:7` 框配置战斗头像。
- 将源图路径和可跨分辨率复现的裁切数据保存到 `#Player.xlsx`。
- 让卡面与裁切参数经 Luban、Go 领域模型和比赛快照传递到客户端。
- TutorialPage 使用完整 `2:3` 卡面，BattlePage 使用动态裁切的 `5:7` 头像。
- 保留 `portrait`，使旧配置、缺图和加载失败场景可以平滑回退。

**Non-Goals**

- 不生成第二张裁切图片，也不提供图片滤镜、旋转、抠图或画质增强。
- 不批量扫描或自动导入用户电脑上的素材目录。
- 不修改 MatchLoop、随机数、战斗数值、事件结构或持久化数据库。
- 不要求本轮统一改造游戏内所有出现选手图片的页面。

## Decisions

### 1. 使用源图加归一化裁切矩形

`#Player.xlsx` 增加以下字段，字段同时参与 Server、Client 和 JSON 导出：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `cardImage` | string | `client/public` 下的项目相对路径，例如 `player-cards/player_niko.png` |
| `avatarCropX` | float | 裁切框左边界占原图宽度的比例 |
| `avatarCropY` | float | 裁切框上边界占原图高度的比例 |
| `avatarCropWidth` | float | 裁切框宽度占原图宽度的比例 |
| `avatarCropHeight` | float | 裁切框高度占原图高度的比例 |

合法矩形满足：四个数均为有限数值，`0 <= x,y < 1`，`0 < width,height <= 1`，`x + width <= 1`，`y + height <= 1`。固定比例依据原图像素计算：

```text
(avatarCropWidth * naturalWidth) / (avatarCropHeight * naturalHeight) = 5 / 7
```

保存和校验允许小量浮点误差。归一化参数不受编辑器显示尺寸、设备像素比或客户端头像尺寸影响，也比保存绝对像素更适合未来替换同构图的高分辨率卡面。

**备选方案：**保存像素坐标。它直观，但会绑定上传时的分辨率，图片替换、压缩或客户端使用不同资源版本后容易失效，因此不采用。

### 2. 完整卡面进入独立受控资源目录

本地服务复用现有受控图片上传机制，将 PNG、JPEG、WebP 复制到 `client/public/player-cards/`，Excel 只保存站点根目录相对路径。服务继续执行扩展名、文件大小、目标目录和重名处理校验，拒绝目录穿越和任意路径写入。

保留现有 `portrait` 字段，不搬迁旧文件。展示回退顺序为：

```text
TutorialPage: cardImage -> portrait -> 默认选手图
BattlePage:   cardImage + AvatarCrop -> portrait -> 默认选手图
```

**备选方案：**复用 `client/public/portraits/`。这会混淆完整卡面和旧头像的资源语义，也不利于后续清理与批量检查，因此使用独立目录。

### 3. 编辑器采用成熟裁切组件并保存百分比结果

Player 专属页引入 `react-image-crop`，固定 `aspect={5 / 7}`，允许拖动和缩放，最终从组件的 percent crop 生成归一化值。该库当前 peer 范围覆盖 React 19，体积较小，并能处理固定比例、边界约束和触摸操作；只在配置工具前端增加依赖，不进入游戏客户端产物。

首次上传或点击“重置裁切”时，编辑器按原图生成居中的最大 `5:7` 矩形。属性区显示只读的 `x/y/width/height` 归一化值，方便排查数据，但主要操作始终通过画面上的裁切框完成。

**备选方案：**自行实现鼠标命中、八向缩放和触摸交互。该方案测试面较大，且没有业务上的差异化收益，因此不采用。

### 4. 编辑器布局和操作流

Player 页面保持现有工作台导航与列表结构，在属性面板增加“选手视觉资源”区。裁切工作区需要足够宽度时可占据编辑主区，不塞入窄属性栏。

```text
+----------------------------------------------------------------------------------+
| 配置工作台 | 地图配置 | Player | Team | TutorialBattle | 通用表格              |
+------------------+---------------------------------------------------------------+
| 选手列表         | Player 属性                                                   |
| [搜索________]   | ID: player_niko   名称: NiKo   战队: G2                      |
| > NiKo           | ...能力值与位置标签...                                        |
|   m0NESY         +---------------------------------------------------------------+
|   ZywOo          | 选手视觉资源                                  [上传卡面]       |
|                  |                                                               |
|                  | 完整卡面              头像裁切                战斗头像预览      |
|                  | +--------------+      +------------------+    +----------+      |
|                  | |              |      |      +-----+     |    |          |      |
|                  | |   2:3 原图   |      |      | 5:7 |     |    |  5:7     |      |
|                  | |  完整显示    |      |      |裁切框|     |    |  结果    |      |
|                  | |              |      |      +-----+     |    |          |      |
```

操作顺序：选择 Player -> 点击“上传卡面” -> 选择本地图片 -> 在中间原图上拖动/缩放 `5:7` 框 -> 检查右侧实时预览 -> 保存 -> 写入 Luban。更换卡面后旧裁切不会盲目沿用，编辑器生成居中默认框并要求重新保存。

### 5. 运行时使用值对象传递裁切数据

Luban 表保持便于策划填写的扁平字段；Go 运行时在适配边界将四个数聚合为可选值对象：

```text
TbPlayer flat fields
  -> PlayerProfile.CardImage + *ImageCrop
  -> PlayerState.CardImage + *ImageCrop
  -> TypeScript BattlePlayer visual fields
```

`ImageCrop` 的 JSON 为 `{ x, y, width, height }`。服务端仅在路径非空且矩形合法时构造该对象，否则输出空裁切并保留 `Portrait`。这样可避免客户端把四个互相关联的数字误当成四个独立状态，也让旧快照字段缺失时自然兼容。

这些字段随已有玩家状态传输，不增加 RPC、Nakama handler、Storage 对象或数据库迁移。静态字段体积很小，不改变 MatchLoop tick、随机数消费顺序和模拟结果。

### 6. 客户端提供两种明确的展示组件

客户端抽出两个展示职责，避免各页面自行解释裁切参数：

- `PlayerFullCard`：固定 `2:3` 容器，完整显示 `cardImage`，用于 TutorialPage。
- `PlayerAvatarCrop`：固定 `5:7` overflow 视口，根据图片自然尺寸和归一化矩形计算缩放及偏移，用于 BattlePage。

`PlayerAvatarCrop` 在图片加载后计算：裁切像素矩形为 `(x*W, y*H, width*W, height*H)`，缩放比例为“视口宽度 / 裁切像素宽度”，再将整图平移至裁切矩形左上角。视口尺寸变化时重新计算，不修改原始配置值。加载失败由统一组件执行回退，死亡灰化继续由 PlayerCard 叠加。

TutorialPage 预期界面：

```text
+--------------------------------------------------------------------------+

+--------------------------------------------------------------------------+
| +---------+ +---------+ +---------+ +---------+ +---------+              |

| | 选手卡  | | 选手卡  | | 选手卡  | | 选手卡  | | 选手卡  |              |
```

桌面端候选区固定为 5 列，15 名候选形成 3 行；移动端降为 2 列。应用壳固定在视口高度内，由主内容区承担纵向滚动，顶部导航和底部阵容操作条保持可见。

BattlePage 保持现有阵容密度，只替换头像内部渲染：


## Risks / Trade-offs

- **新增列会影响已有导表产物。** 使用可选路径和零值裁切字段，先更新 Excel/生成代码，再更新运行时映射；旧 `portrait` 始终保留。
- **浮点比率可能产生细小误差。** 编辑器输出限制精度，服务端和校验器采用统一容差，不要求浮点绝对相等。
- **原图过大可能拖慢编辑器。** 继续限制上传文件大小；裁切交互只显示浏览器缩放图，保存的参数仍基于自然尺寸。
- **卡面替换后构图可能变化。** 更换文件时重置为居中裁切，防止旧参数静默指向错误区域。
- **运行时字段增加快照体积。** 每名选手只增加一个短路径和四个数，第一版接受该成本；不因此引入独立资源查询 RPC。
- **第三方裁切组件增加维护面。** 锁定具体依赖版本，并用组件测试覆盖固定比例、边界和 percent crop 转换。

## Migration Plan

1. 在 `#Player.xlsx` 增加新列并配置空路径/零值默认值，运行 Luban 生成 Server、Client 和 JSON 结构。
2. 将首批 23 张选手卡面复制到 `client/public/player-cards/`；按现有 Player ID 可靠匹配 18 名选手，重复版本作为可选素材保留，`chopper` 与 `kyxsan` 因无同名素材继续使用 `portrait`。
3. 为已匹配 Player 写入卡面路径和居中上半身的合法 `5:7` 初始裁切，之后可由策划逐人微调。
4. 扩展配置工作台上传服务、Player 表解析、裁切 UI、校验和 Excel 写回。
5. 扩展 Go `PlayerProfile`、`PlayerState` 和投影映射，验证旧配置仍可创建比赛。
6. 在客户端接入统一的完整卡面与裁切头像组件，分别替换 TutorialPage 和 BattlePage 的对应视觉区域。
7. 运行编辑器测试、客户端测试与构建、Go 测试、Luban 导表，并按 README 使用 Docker 编译 Nakama 插件。

回滚时恢复客户端旧 `portrait` 渲染并停止读取新字段即可；由于 `portrait` 未删除，Excel 新列可暂时保留而不影响旧流程，不需要回滚用户上传的源图。

无。当前已确认完整卡面用于配置工作台和 TutorialPage，比赛过程使用 `5:7` 动态裁切头像；裁切数据进入策划表，且不生成第二张图片。
