## Context

当前 `BattlePage` 在桌面端使用“左侧阵容 + 中央雷达和播报 + 右侧阵容”的三栏结构。手机端样式主要隐藏 `.battle-roster`、缩小标题与间距，但中央区域仍沿用固定高度和桌面组件顺序，因此存在以下问题：

- 手机首屏被较大的页头、比分和回合按钮占用，核心赛况需要长距离滚动。
- 两侧阵容被直接隐藏，用户无法判断双方当前存活状态。
- 炸弹、雷达和实时播报是三个独立面板，缺少连续的比赛观察体验。
- `MapView` 的底图使用 `object-contain`，标记却相对于整个外层容器按百分比定位。容器宽高比与雷达图不同时，底图产生留白而标记层不产生同样的变换，导致窗口缩放后标记偏移。
- `.battle-shell` 使用固定高度和 `overflow: hidden`，在移动端可能裁掉超出视口的内容。

对本地下载的 HLTV 手机比赛页进行只读检查后，可以确认其核心思路是：窄屏使用自然纵向流，将回合状态、雷达、双方存活状态和紧凑事件流组织在同一个比赛区域中，而不是整体缩小桌面页面。本设计借鉴其信息层级，但不复制其 DOM、样式、图片或品牌表现。

现有服务端已经提供完整 `MatchReport`、当前回合阵营分配、选手状态、事件位置和最终统计。本变更无需扩展 Nakama RPC、Match Handler、Storage 或 Luban 配表。

## Goals / Non-Goals

**Goals:**

- 在约 390px 的手机视口中优先展示比分、回合、控制、雷达、存活状态和最近事件。
- 保留阵容、完整实时战况和数据统计能力，不再通过 `display: none` 永久丢弃移动端功能。
- 保证雷达底图与事件标记在任意响应式尺寸、设备方向和浏览器缩放下保持一致。
- 让桌面和移动端共享同一份回放控制状态与服务器权威数据。
- 保持桌面端现有信息密度和主要工作流，避免为了手机端重写比赛逻辑。
- 为 390px 手机、横屏/平板和 1440px 桌面建立自动化与截图验证。

**Non-Goals:**

- 不修改模拟规则、击杀位置采样、事件顺序、胜者计算或 MatchLoop。
- 不新增实时网络同步、观战协议或服务器接口。
- 不复制 HLTV 的视觉资源、网页代码或完整产品导航。
- 不在本变更中重新设计 Home、Tutorial、Friends 等其他页面。
- 不增加雷达缩放、拖拽或手势导航；雷达在移动端完整适配容器。
- 不把完整桌面选手卡原样压缩进 390px 双栏。

## Decisions

### 1. BattlePage 持有回放状态，布局组件只负责表现

`BattlePage` 继续持有 `roundIndex`、`furthestRoundIndex`、`visibleEventCount`、`playing` 和 `fullMatchRevealed`。实现时将当前 JSX 编排拆为：

```text
BattlePage（服务器战报 + 回放控制器 + 派生状态）
├── DesktopBattleLayout（>= 1024px）
└── CompactBattleLayout（< 1024px）
    ├── MobileScoreHeader
    ├── MobileReplayControls
    ├── MobileLiveStage
    │   ├── BombStatusStrip
    │   ├── ResponsiveMapView
    │   ├── AlivePlayersStrip
    │   └── CompactEventFeed
    └── BattleAuxTabs
        ├── 实时战况
        ├── 阵容
        └── 数据统计
```

布局选择使用浏览器 `matchMedia` 的轻量 Hook，不引入响应式运行时依赖。桌面和紧凑布局不会同时挂载，避免产生两个 Dialog、两个自动滚动容器或重复焦点目标。断点切换只替换表现组件，回放状态保留在父层，因此旋转设备或调整窗口不会重新开始比赛。

选择 `< 1024px` 作为紧凑布局范围，是因为三栏阵容在 768px 至 1023px 已难以保持可读；紧凑布局内部再通过 CSS Grid 在平板宽度增加留白或双列辅助内容。桌面规约从 1024px 开始，边界清晰。

**替代方案：**仅用 CSS 重排当前 DOM。该方案改动较少，但难以同时处理桌面三栏、移动页签、焦点顺序和隐藏组件副作用，因此不采用。

### 2. 使用共享的 BattleViewModel 防止双布局逻辑分叉

从现有派生逻辑形成只读 `BattleViewModel`，至少包含：

- 当前双方队伍与选手状态。
- 当前回合、阶段、T/CT 分配和比分。
- 当前可见事件、炸弹状态和已揭示回合集合。
- 播放、暂停、跳过和选择回合的命令。
- 当前统计和格式化事件所需上下文。

`DesktopBattleLayout` 与 `CompactBattleLayout` 消费同一对象。存活条直接读取当前已播放位置派生的 `BattlePlayer.alive`，不得从回合最终快照提前暴露死亡结果。阵营颜色根据当前回合 `team_t_id` / `team_ct_id` 映射，而不是永久绑定 Team A 或 Team B。

**替代方案：**让移动组件再次遍历事件并独立计算比分、生命和统计。该方案会产生桌面与移动端结果不一致，因此不采用。

### 3. 雷达底图和事件标记统一到 SVG 坐标空间

Dust2 雷达资源自然坐标作为 SVG 视口：

```text
viewBox = 0 0 1024 984
svg 容器宽高比 = 1024 / 984
markerX = location.x * 1024
markerY = location.y * 984
```

底图通过同一 SVG 内的 `<image x="0" y="0" width="1024" height="984">` 渲染，击杀和炸弹标记作为同一 SVG 的后续图层。根 SVG 负责等比缩放，底图和标记天然共享变换，不再依赖外层 `div` 的百分比定位或 `object-fit` 留白计算。

合法事件坐标为 `0..1`。越界或非有限值不绘制标记，并在开发模式提供可定位警告，客户端不得擅自把非法坐标改成另一个有效地点。标记继续只使用当前选中回合已经可见的服务器事件。

**替代方案：**

- CSS 百分比 + 计算底图实际矩形：需要 `ResizeObserver` 和留白换算，容易在字体、滚动条和设备像素比变化时回归。
- Canvas：适合大量动态图元，但当前每回合标记很少，且 Canvas 的可访问性、测试和交互成本更高。

因此选用 SVG，不新增图形库。

### 4. 移动端采用连续比赛舞台，而不是嵌套卡片

默认“实时战况”布局如下：

```text
┌──────────────────────────────────┐
│ 比赛进行中             玩家 / 登录 │  紧凑页头
├──────────────────────────────────┤
│ 你的临时阵容   4 : 6   Vitality   │
│       T     第 11 回合     CT      │
├──────────────────────────────────┤
│ [暂停] [跳过比赛]   ‹ 10  11  12 ›│
├──────────────────────────────────┤
│ 炸弹：已下包                  B 区 │
│                                  │
│           Dust2 雷达              │
│        击杀点 / 炸弹事件           │
│                                  │
│ T  ● ● ● ○ ○      ● ● ● ● ○  CT │
│                                  │
│ [CT] apex  M4A1-S  [T] donk      │
│ [T]  NiKo  AK-47   [CT] mezii    │
│ CT 赢得回合：拆除炸弹              │
├──────────────────────────────────┤
│ [实时战况]      [阵容]      [统计] │
└──────────────────────────────────┘
```

雷达、存活条和最近事件位于同一个全宽区域，不再分别放入嵌套卡片。炸弹状态作为舞台顶部的状态条。最近事件默认保留约 5 条，最新事件保持可见；用户点击“实时战况”可浏览当前回合全部已播放事件。

主要触控按钮至少 44px。回合导航只在自己的横向区域内滚动，不允许造成页面级横向滚动。移动页面使用 `min-height: 100dvh`、自然纵向滚动和安全区内边距，不再继承桌面 `height: 100%` 与 `overflow: hidden`。

### 5. 阵容和统计使用页签保留，而不是在手机端隐藏

点击底部页签后的预期如下：

```text
阵容页签
┌──────────────────────────────────┐
│ [你的临时阵容 T] [Vitality CT]    │  队伍切换
│ donk       100 HP      AK-47     │
│ kyousuke     0 HP      已阵亡     │
│ ...                              │
└──────────────────────────────────┘

统计页签
┌──────────────────────────────────┐
│ 选手             K    D    A     │
│ donk              8    4    1     │
│ apex              4    3    2     │
│ ...                              │
└──────────────────────────────────┘
```

- 点击“实时战况”：返回同一回合、同一事件进度的比赛舞台。
- 点击“阵容”：默认显示用户上次查看的队伍，首次进入显示 Team A；顶部使用 T/CT 和队名明确当前阵营。
- 点击另一队：切换五人列表，不改变回放状态。
- 点击“统计”：显示现有实时 K/D/A；比赛结束后继续使用服务端最终统计入口。

移动页签是客户端临时 UI 状态，无需写入 Storage；刷新页面后按现有 BattlePage 恢复规则处理。

### 6. 移动事件流使用结构化摘要，完整语义仍保留

`formatBattleEvent` 继续负责完整中文战报；新增紧凑格式化层只消费同一 `GameEvent` 和 `BattleEventContext`。典型结果为：

```text
[CT] apex  M4A1-S  [T] donk
[T] NiKo  →  [CT] mezii  -52 HP
炸弹已在 B Site 安放
CT 赢得回合：拆除炸弹
```

击杀行优先保留阵营、双方选手和武器。宽度不足时允许在语义边界换行，不使用动态视口字号压缩文本。完整实时战况仍显示完整本地化句子，因此紧凑摘要不会损失用户可访问的信息。

### 7. 依赖、Nakama 与状态同步兼容性

- React 运行时代码使用现有 React、TypeScript、Tailwind/CSS 和 Lucide，不新增运行时 npm 包。
- 当前仓库测试脚本只运行 Node 测试，无法真实验证 CSS 布局。实现阶段新增 `@playwright/test` 作为开发依赖，用于 390x844、844x390、1024x768 和 1440x900 视口测试；该依赖不进入运行时业务包。
- Nakama 插件、RPC、Match Handler、Storage、数据库和 Luban 均不改动。
- MatchLoop tick、服务器状态同步频率、战报生成和事件位置采样均不受影响。
- 客户端仅从现有服务器状态派生表现，不向服务器写入移动端页签或布局状态。

## Risks / Trade-offs

- **[风险] 桌面与移动布局逐渐出现功能差异** → 通过共享 `BattleViewModel`、共享 MapView/格式化器和跨视口端到端用例约束行为一致。
- **[风险] 断点切换导致回放重置或计时器重复** → 回放状态和计时 Effect 保留在 `BattlePage`，布局组件无权启动独立播放循环。
- **[风险] SVG 坐标正确但雷达资源本身含有未知内边距** → 以实际 1024x984 图片边界和配置编辑器的 `0..1` 坐标约定建立中心、四角及已知点位截图测试。
- **[风险] 最近事件覆盖过多地图空间** → 最近事件放在雷达下方的同一舞台中而不是遮挡雷达；默认限制约 5 条，完整列表放入实时战况视图。
- **[风险] 手机页签隐藏了正在更新的信息** → 隐藏页签只隐藏表现，BattlePage 回放控制器继续推进；返回实时战况时呈现最新已播放状态。
- **[取舍] 紧凑布局覆盖平板** → 小于 1024px 使用紧凑信息架构可避免三栏过窄；平板通过更宽的内部网格利用额外空间。

## Migration Plan

1. 先提取共享 `BattleViewModel` 和回放命令，确保现有桌面快照与行为不变。
2. 将 `MapView` 迁移为 SVG 统一坐标实现，并用坐标单元测试和多视口截图确认标记对齐。
3. 把现有桌面 JSX 移入 `DesktopBattleLayout`，完成桌面回归验证。
4. 增加 `CompactBattleLayout`、存活条、紧凑事件流和辅助页签。
5. 调整 BattlePage 响应式滚动、安全区和中间宽度样式。
6. 运行前端类型检查、Node 测试、Playwright 多视口测试和生产构建，再重建本地前端 Docker 镜像验证 `/battle`。

本变更无数据迁移。若移动布局出现严重回归，可回滚布局选择和新组件并恢复旧 BattlePage 编排；服务器、数据库和配置文件无需回滚。

## Open Questions

当前没有阻塞实施的问题。第一版采用以下默认值，后续可根据真机测试微调而无需改变规约：

- 移动端默认页签为“实时战况”。
- 最近事件默认显示约 5 条，优先保证当前回合结果可见。
- 紧凑布局断点为 1024px，平板使用同一信息架构但允许更宽的内部排列。
