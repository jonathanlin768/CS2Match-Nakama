## 1. 设计目的

本模块是 CS2Match 项目的**核心玩法模块**，负责实现模拟 CS2 对战的自动演算与战报播放。

区别于传统 FPS 游戏的实时操作，本模块采用**"路线对决 + 数值碰撞"**的回合制设计，以 HLTV 文字直播的形式呈现比赛过程。MVP 阶段中，玩家在赛前组建自己的选手阵容后，由服务器自动完成整场比赛的推演（包括路线选择、对决演算、胜负判定），客户端仅负责接收完整战报并按节奏播放。

**设计目标**：
- 在 MVP 阶段实现一个**可运行、观感接近HLTV文字直播**的最小对战系统
- 服务器自动推演，客户端纯播放，前后端职责清晰
- 为后续版本（教练技能、更多地图、经济系统）预留扩展接口
- 前后端数据流转清晰，便于快速实现

## 2. 功能总览

### 2.1 一句话描述

两支各由 5 名选手组成的队伍（T 与 CT），在 Dust2 地图上由服务器自动推演进行回合制对决，以 HLTV 文字直播的形式呈现击杀播报和数据统计，先达到 13 分的队伍获胜。MVP 阶段教练玩家不进行任何局内操作，仅观看战报播放。

### 2.2 核心流程图

```
[赛前准备]
    │ 双方教练各自选择 5 名选手组成阵容
    │ 确定 T/CT 方（先攻方随机分配）
    ▼
[客户端发起开战请求]
    │ 携带双方阵容信息、地图信息
    ▼
[服务器自动推演整场比赛]
    │
    ├── 逐回合演算:
    │   ├── T方进攻路线（服务器随机选择）
    │   ├── CT方防守配置（服务器自动分配）
    │   ├── 路线对决 → 生成击杀事件
    │   ├── 下包/回防/拆包判定
    │   └── 回合结算 → 比分更新
    │
    ├── 半场检查（满12回合交换阵营）
    │
    └── 生成完整战报（含所有回合事件+统计）
    ▼
[服务器返回战报]
    ▼
[客户端战报播放]
    │ 按时间间隔逐条展示HLTV文字播报
    │ 展示实时比分、存活人数、数据统计
    ▼
[比赛结束] → 展示战后统计界面
```

### 2.3 功能边界

| 范围 | 说明 |
|------|------|
| 地图 | 仅 Dust2（de_dust2） |
| 阵营 | T（恐怖分子） vs CT（反恐精英） |
| 回合数 | BO24（先到13分获胜），平局 12:12 时继续直至分出胜负 |
| 选手数 | 每方 5 人，共 10 个"单位" |
| 教练操作 | **MVP阶段教练无任何局内操作**，服务器自动完成所有决策 |
| 核心交互 | 赛前选阵 → 发起开战请求 → 客户端播放战报 |

## 3. 核心机制设计

### 3.1 基础规则

1. **回合制**：比赛由多个回合组成，每回合独立计算。
2. **教练角色（MVP）**：玩家扮演教练，**仅负责赛前组建阵容**。局内无任何操作——所有路线选择、战术决策均由服务器自动随机决定。教练仅观看战报播放。
3. **选手AI**：所有选手行为由服务器自动演算，基于数值和路线配置进行对决。
4. **生命值**：每名选手每回合 100 HP，归零即死亡，退出当前回合。
5. **武器**：MVP 阶段所有选手默认使用主战武器（AK-47 for T, M4A4 for CT），不考虑经济购买和武器切换。
6. **护甲**：所有选手默认携带防弹衣+头盔（100 护甲），作为独立计算减伤。
7. **全自动推演**：客户端发起一次开战请求后，服务器在后台完成整场比赛（全部回合）的推演，将完整战报作为响应返回。客户端逐条播放，期间不再与服务器通信。

### 3.2 路线对决机制

#### 3.2.1 对决触发

当进攻方被服务器分配到某条路线后，该路线上会分配若干名进攻选手。防守方由服务器根据预设规则自动分配防守选手到各条路线。当同一条路线上同时存在双方存活的选手时，触发对决。

> **MVP 阶段路线分配方式**：每回合 T 方的进攻路线由服务器从 6 条可选路线中**按均等概率随机选择 1 条主路线**，并以 30% 概率附加 1 条通向同一包点的副路线（触发夹击）。CT 方的防守配置由服务器根据进攻路线自动分配（进攻 A 区则 CT 重 A 防守，进攻 B 区则 CT 重 B 防守）。

#### 3.2.2 对决流程

```
路线对决（单条路线）
    │
    ├── 1. 确定路线上的双方选手列表
    │       T: [选手A, 选手B]  CT: [选手X, 选手Y]
    │
    ├── 2. 按【突破】属性从高到低排序，确定交火顺序
    │       排序后: 选手A(突破85) > 选手B(突破60)
    │                选手X(突破70) > 选手Y(突破50)
    │
    ├── 3. 依次进行 1v1 对决
    │       选手A vs 选手X → 计算胜负
    │       胜者继续，败者死亡
    │       若平局（双方同时存活），进行第二轮
    │
    ├── 4. 存活选手继续推进/留守
    │       若T方全灭 → 该路线进攻失败
    │       若CT方全灭 → T方推进至包点
    │       若双方均有存活 → 标记为"僵持"，进入下一回合阶段
    │
    └── 5. 生成击杀事件，输出HLTV播报
```

#### 3.2.3 对决伤害计算

单次对决的伤害计算：

```
基础伤害 = 攻击方火力值 × 0.5 + 武器基础伤害
实际伤害 = 基础伤害 × (1 + 突破值差值系数) × 护甲减伤系数

其中:
  突破值差值系数 = (攻方突破 - 守方突破) × 0.005  // 每点差值 ±0.5%
  护甲减伤系数 = 1 - (守方护甲值 × 0.00065)       // 100甲 = 65%减伤
  
命中判定:
  攻击方命中率 = 50% + (精准值差值 × 0.1) + 随机波动(-5% ~ +5%)
  // 突破对决时，命中率受精准属性影响
```

单次对决最多进行 **3 轮**。3轮后若双方均未死亡，判定为"僵持"，双方各自退回，不生成击杀。

#### 3.2.4 补枪机制

当一名选手被击杀后，同路线上存活的队友有概率触发"补枪"：

```
补枪触发概率 = 队友补枪值 × 0.8%  // 最大 80%
补枪成功概率 = 补枪者补枪值 × 0.9%  // 最大 90%

若补枪成功 → 击杀对方存活选手中的一名（随机选择）
```

### 3.3 攻守转换与下包

#### 3.3.1 下包触发条件

- T方至少有 1 名选手存活到达包点（通过某条路线全灭CT方或该路线无CT防守）
- 当前回合时间 > 0
- 该回合尚未下过包

#### 3.3.2 下包流程

```
下包阶段
    │
    ├── 1. 存活T方选手执行下包（消耗 5 秒模拟时间）
    │       下包期间若CT存活选手到达 → 打断下包，进入对决
    │
    ├── 2. 下包成功 → 炸弹计时器启动（模拟 40 秒）
    │       播报: "炸弹已被安放。"
    │
    ├── 3. CT方回防路线（服务器自动选择）
    │       根据下包位置，从可用回防路线中随机选择1条:
    │       A区下包 → A大回防 / A小回防 / CT中回防
    │       B区下包 → B洞回防 / B门回防 / CT中回防
    │       CT存活选手按路线最大人数限制自动分配到回防路线
    │
    ├── 4. 回防路线对决
    │       与进攻路线对决使用相同规则
    │
    └── 5. 炸弹爆炸 或 拆包成功 或 全灭
```

#### 3.3.3 拆包

CT方存活选手到达包点后执行拆包（消耗 10 秒模拟时间）。拆包期间若被击杀则打断。下包后 CT 全灭则直接爆炸。

### 3.4 时间模拟

MVP 阶段不使用真实时间推进，采用**"阶段推进"**机制：

| 阶段 | 模拟时间 | 说明 |
|------|---------|------|
| 开局 | 0s | 回合开始，教练选择路线 |
| 进攻推进 | 10-20s | 取决于路线长度（长路20s，短路10s） |
| 路线对决 | 5-15s | 取决于交火轮数 |
| 下包 | 5s | 固定 |
| 炸弹倒计时 | 40s | 固定 |
| 拆包 | 10s | 固定 |
| 回合上限 | 115s | 超过即CT胜（时间耗尽） |

时间仅用于**播报中的时间戳展示**和**回合超时判定**，不影响实际推演速度。服务器可在毫秒级完成整个回合演算。

### 3.5 模拟时间估算方法

#### 3.5.1 为什么要估算时间

HLTV 文字直播的核心观感来自**时间戳的真实感**。如果一局 30 回合的比赛每回合都在 0:05-0:10 内结束，或者每回合都拖到 1:45，都会让玩家感觉不真实。我们需要一套规则，让服务器生成的模拟时间既符合 CS2 真实比赛的节奏分布，又有足够的随机变化。

#### 3.5.2 真实 CS2 比赛的时间特征

基于真实 CS2 职业比赛的统计规律：

| 回合结果类型 | 占比 | 典型时长 | 说明 |
|-------------|------|---------|------|
| CT 全胜（T全灭未下包） | ~35% | 45-75s | CT防守成功，T方进攻被完全拦截 |
| T 全胜（CT全灭） | ~20% | 30-60s | T方突破迅速，速推成功 |
| 炸弹爆炸 | ~25% | 80-105s | 下包后CT未能及时拆包 |
| 拆包成功 | ~12% | 75-100s | 下包后CT成功回防拆包 |
| 时间耗尽 | ~8% | 115s | T方迟迟未能突破或下包 |

**关键规律**：
- 约 55% 的回合在 60 秒内结束（一方全灭）
- 约 25% 的回合涉及下包+爆炸（较长）
- 极少数回合拖到时间耗尽（~8%）
- 首杀通常发生在 15-35 秒之间

#### 3.5.3 模拟时间生成规则

服务器在推演每个回合时，根据回合的实际走向动态计算模拟时间：

**Step 1: 基础推进时间**

```
路线推进时间 = 路线基础长度 + 随机波动(-3s, +5s)

A大/中夹B (长路线): 18-25s
A小/B洞 (中路线): 12-18s
B门/RushB (短路线): 8-13s
```

**Step 2: 首杀时间**

```
首杀时间 = 推进时间 + 交火延迟 + 随机波动

交火延迟取决于双方突破值差距:
  差距 > 20: 1-3s (快速首杀)
  差距 10-20: 2-5s
  差距 < 10: 4-8s (僵持后首杀)
  差距 ≈ 0: 6-10s ( prolonged duel)
```

**Step 3: 后续击杀时间**

```
每条路线上的后续击杀，每条间隔 1-4s（随机）
补枪事件固定 +1s
```

**Step 4: 下包阶段时间（如触发）**

```
下包时间 = 当前时间 + 5s (固定)
```

**Step 5: 回防阶段时间（如触发）**

```
回防推进时间 = 回防路线长度 + 随机波动(-2s, +3s)
回防对决时间 = 同 Step 2/3 规则
```

**Step 6: 最终时间校正**

```
根据回合结果进行校正:
- 若T全灭未下包:  最终时间 = 最后击杀时间 + 2-5s
- 若CT全灭:       最终时间 = 最后击杀时间 + 2-5s
- 若炸弹爆炸:     最终时间 = 下包时间 + 40s (固定)
- 若拆包成功:     最终时间 = 拆包开始时间 + 10s
- 若时间耗尽:     最终时间 = 115s (固定上限)

所有时间不超过 115s，超过则强制截断并判定为时间耗尽。
```

#### 3.5.4 时间分布验证

按上述规则运行 1000 场模拟的期望分布：

| 时长区间 | 期望占比 | 对应结果类型 |
|---------|---------|-------------|
| 20-45s | ~15% | 速推/速防 |
| 45-75s | ~40% | 正常全灭局 |
| 75-95s | ~25% | 下包+回防局 |
| 95-115s | ~12% | 长残局/时间耗尽 |
| 115s | ~8% | 时间耗尽 |

这个分布与真实 CS2 比赛数据大致吻合，能营造出真实的观赛节奏。

#### 3.5.5 客户端播放节奏

服务器生成的模拟时间戳仅用于展示，客户端的**播放速度**可独立控制：

```
默认播放速度:  真实时间的 1x（服务器生成的时间戳按原速展示）
加速模式:      2x / 4x
暂停:          玩家可随时暂停
跳过:          可跳至下一回合开始
```

播放节奏与模拟时间解耦，确保玩家既可以选择沉浸式慢速观看，也可以快速浏览整场比赛。

## 4. 地图与路线系统（Dust2）

### 4.1 进攻路线

T方开局可选的 6 条进攻路线：

| 路线ID | 路线名称 | 目标包点 | 路线长度 | 最小人数 | 最大人数 | 说明 |
|--------|---------|---------|---------|---------|---------|------|
| A_Long | A大 | A包 | 长（20s） | 1 | 3 | 经典A大爆弹，突破后可控制A包点 |
| A_Short | A小 | A包 | 中（15s） | 1 | 2 | 从A小楼梯上，适合配合A大夹击 |
| B_Tunnel | B1（B洞） | B包 | 中（15s） | 1 | 3 | 从B洞出，可直接进入B包点 |
| B_Door | B2（B门） | B包 | 短（10s） | 1 | 2 | 从中门转B，速度快但易被拦截 |
| Rush_B | RushB | B包 | 短（10s） | 2 | 5 | 全员冲B洞，牺牲战术多样性换速度 |
| Mid_SplitB | 中夹B | B包 | 长（20s） | 2 | 4 | 中门控制后分两路夹B |

#### 4.1.1 路线特性

- **路线长度**：影响推进时间和CT准备时间。长路线给CT更多防守布置时间，但可能暴露更少信息。
- **最小/最大人数**：每条路线有参与人数限制。RushB需要至少2人才能发挥人数优势。
- **夹击效果**：若同一回合选择两条通向同一包点的路线（如A大+A小），触发"夹击"加成：所有参与夹击路线的选手突破值 +5。

#### 4.1.2 路线自动选择规则（MVP）

MVP 阶段无需教练选择，服务器按以下规则自动决定：

- **主路线**：每回合从 6 条进攻路线中等概率随机选择 1 条
- **副路线**：30% 概率附加 1 条与主路线通向同一包点的路线（触发夹击加成）
- **选手分配**：5 名 T 方选手按路线最大人数限制随机分配到主/副路线上
- **CT 防守**：根据 T 方选择的包点自动配置防守侧重（A 区 → 重 A，B 区 → 重 B）

> 后续版本中路线选择将交给教练决策，夹击策略和选手分配将成为战术层面的核心玩法。

## 5. 选手数值体系

### 5.1 基础属性

每名 CS2 选手拥有以下 6 项核心属性：

| 属性名 | 英文ID | 取值范围 | 说明 | 在对决中的作用 |
|--------|--------|---------|------|--------------|
| **突破** | Entry | 1-100 | 首杀能力、打开局面的意识 | 决定交火顺序、影响伤害加成 |
| **精准** | Aim | 1-100 | 瞄准精度、爆头率 | 影响命中率判定 |
| **补枪** | Trade | 1-100 | 队友倒下后的补枪成功率 | 触发补枪事件的概率和成功率 |
| **残局** | Clutch | 1-100 | 1vN情况下的胜率 | 人数劣势时的属性加成 |
| **火力** | Firepower | 1-100 | 持续输出能力、控枪稳定性 | 影响基础伤害值 |
| **意识** | GameSense | 1-100 | 地图意识、信息读取、预判 | 影响防守方预瞄优势、残局信息判断 |

#### 5.1.1 属性设计原则

- 每项属性独立，不存在"总战力"之类的汇总值
- 真实职业选手的属性范围大致在 **60-95** 之间，顶尖选手单项可达 90+
- 普通/新秀选手属性范围在 **40-70** 之间
- 属性差异通过对战公式转化为胜负概率，而非绝对值比较

### 5.2 位置标签

每名选手拥有 1-2 个位置标签，影响路线选择时的属性加成：

| 位置标签 | 说明 | 路线加成 |
|---------|------|---------|
| **突破手** (Entry) | 负责首杀开路 | 在第一条进攻路线突破 +10 |
| **狙击手** (AWPer) | 使用AWP进行远距离击杀 | 在长路线（A大、中夹B）火力 +15，短路线火力 -10 |
| **指挥** (IGL) | 团队战术决策者 | 全队意识 +5（仅当局内存活时） |
| **自由人** (Lurker) | 单走寻找击杀机会 | 在第二条路线/副路线全属性 +8 |
| **补枪手** (Support) | 负责道具和补枪 | 补枪属性 +15 |
| ** Anchor** (守点者) | 负责包点防守 | 在回防路线防守时意识 +10 |

#### 5.2.1 标签与属性关系

位置标签**不直接决定属性值**，而是提供路线/场景加成。属性值是选手的"硬实力"，标签决定"场景适应性"。

例如：
- s1mple：狙击手标签，Aim 95, Firepower 90 → 在长路线极具威胁
- NiKo：突破手标签，Entry 93, Aim 92 → 在进攻第一条路线时几乎必拿首杀
- Xyp9x：补枪手标签，Trade 90, Clutch 88 → 队友倒下后大概率换到人

### 5.3 战斗公式

#### 5.3.1 完整对决流程

```
def 路线对决(进攻方列表, 防守方列表, 路线类型):
    
    // 1. 应用位置标签加成
    进攻方列表 = 应用进攻加成(进攻方列表, 路线类型)
    防守方列表 = 应用防守加成(防守方列表, 路线类型)
    
    // 2. 按突破值排序确定交火顺序
    所有选手 = 合并并按突破值降序排列(进攻方列表, 防守方列表)
    
    // 3. 逐一对决
    击杀事件列表 = []
    
    while 存在双方存活选手:
        当前攻击者 = 取存活中突破值最高者
        目标 = 选择目标(当前攻击者, 对方存活列表)
        
        // 进行最多3轮
        for 轮数 in 1..3:
            result = 单轮对决(当前攻击者, 目标)
            
            if result.击杀者:
                击杀事件列表.push(result)
                标记死亡(result.被击杀者)
                
                // 检查补枪
                if 被击杀方有存活队友:
                    trade_result = 尝试补枪(被击杀方队友, 击杀方)
                    if trade_result:
                        击杀事件列表.push(trade_result)
                break
            
            if 轮数 == 3:  // 僵持
                标记僵持(当前攻击者, 目标)
                break
    
    return 击杀事件列表, 存活列表


def 单轮对决(攻击者, 防守者):
    
    // 计算命中率
    命中差值 = 攻击者.精准 - 防守者.意识
    基础命中率 = 50 + 命中差值 * 0.1  // 百分比
    随机波动 = random(-5, 5)
    最终命中率 = clamp(基础命中率 + 随机波动, 10, 95)  // 最低10%，最高95%
    
    // 判定命中
    if random(0, 100) > 最终命中率:
        return {命中: false}  // 未命中
    
    // 计算伤害
    突破差值 = 攻击者.突破 - 防守者.突破
    伤害加成 = 1 + 突破差值 * 0.005
    
    基础伤害 = 攻击者.火力 * 0.5 + 武器基础伤害
    护甲减伤 = 1 - 防守者.当前护甲 * 0.00065
    
    实际伤害 = 基础伤害 * 伤害加成 * 护甲减伤 * 随机波动(0.9, 1.1)
    
    // 应用伤害
    防守者.当前HP -= 实际伤害
    防守者.当前护甲 -= 实际伤害 * 0.5  // 护甲吸收50%伤害
    
    if 防守者.当前HP <= 0:
        return {命中: true, 击杀: true, 击杀者: 攻击者, 被击杀者: 防守者, 伤害: 实际伤害}
    
    // 若未死，防守方反击（简化版，双方同时开火）
    // 防守方命中率计算同理...
    
    return {命中: true, 击杀: false, 伤害: 实际伤害}
```

#### 5.3.2 残局加成

当某一方存活人数 <= 2 且对方存活人数 >= 3 时，触发残局加成：

```
残局加成系数 = 1 + (劣势方人数差 × 0.05)  // 最大 +15%
劣势方所有属性 *= 残局加成系数
```

例如：1v3 时，劣势方全属性 +10%；1v4 时 +15%。

## 6. 回合流程设计

### 6.1 回合阶段

```
回合生命周期（服务器自动推演）
├── 1. SETUP 阶段（自动布置）
│   ├── 服务器: 随机选择T方主路线 + 可选副路线
│   ├── 服务器: 自动分配选手到各路
│   ├── 服务器: 根据进攻目标自动配置CT防守侧重
│   └── 服务器: 自动分配CT选手到各防守位置
│
├── 2. EXECUTE 阶段（进攻执行）
│   ├── 各路线上推进
│   ├── 触发路线对决
│   ├── 生成击杀事件
│   └── 存活选手标记位置
│
├── 3. POST_PLANT 阶段（下包/回防）
│   ├── 若T方到达包点 → 下包
│   ├── 服务器自动选择CT回防路线
│   ├── 回防路线对决
│   └── 拆包/保枪判定
│
├── 4. RESOLVE 阶段（回合结算）
│   ├── 判定胜负原因
│   ├── 计算回合统计数据
│   ├── 输出HLTV播报总结
│   └── 准备下一回合
```

### 6.2 胜负判定

| 结果 | 条件 | 得分方 |
|------|------|--------|
| T胜利-炸弹爆炸 | 下包后CT未能在40秒内拆包 | T |
| T胜利-全歼CT | CT方5人全部死亡 | T |
| CT胜利-全歼T | T方5人全部死亡且未下包 | CT |
| CT胜利-拆包成功 | 成功拆除炸弹 | CT |
| CT胜利-时间耗尽 | 回合时间到达115秒T仍未下包 | CT |
| T胜利-CT保枪 | 下包后CT选择不救（弃枪保甲） | T |

### 6.3 半场切换

- 打完第 12 回合后，双方交换阵营（T变CT，CT变T）
- 比分 >= 13 的一方直接获胜（提前结束）
- 交换后重新进行路线和防守配置选择

### 6.4 比赛结束

| 条件 | 结果 |
|------|------|
| 任意一方达到 13 分 | 该方获胜 |
| 24 回合后比分相同 | 进入加时（先16分获胜，每6回合换边） |

## 9. 前后端交互设计（MVP 简化版）

### 9.1 架构变更说明

MVP 阶段不启用 Nakama Match Handler 的实时推送模式。改为 **RPC 请求/响应模式**：

```
客户端                         服务器
  │                              │
  ├── 1. RPC "StartMatch" ─────►│
  │   {teamA, teamB, mapId}      │
  │                              │ 2. 自动推演整场比赛
  │                              │    （全部回合计算完成）
  │                              │
  │◄────────── 3. 返回完整战报──┤
  │   {rounds[], stats, winner}  │
  │                              │
  ├── 4. 客户端本地播放战报─────┤
  │   （逐条事件按节奏展示）      │  （无需服务器参与）
```

**理由**：MVP 阶段教练无任何局内操作，不需要实时双向通信。RPC 一次请求/响应即可完成全部推演，客户端本地播放。

### 9.2 消息类型（Opcode —— 仅战报播放用）

以下 Opcode 仅用于客户端内部状态机和战报数据结构，**不用于网络通信**：

```go
const (
    // 战报事件类型（仅客户端本地使用）
    EventMatchStart     = 10 // 比赛开始
    EventRoundStart     = 11 // 回合开始
    EventKill           = 12 // 击杀事件
    EventBombPlant      = 13 // 下包
    EventBombDefuse     = 14 // 拆包
    EventBombExplode    = 15 // 炸弹爆炸
    EventRoundEnd       = 16 // 回合结束
    EventMatchEnd       = 17 // 比赛结束
    EventHalfTime       = 18 // 半场切换
    EventClutch         = 19 // 残局触发
)
```

### 9.3 状态同步策略（MVP）

采用**"全量战报返回 + 客户端本地播放"**：

```
流程:
├── 1. 客户端准备开战
│   └── 收集双方阵容信息（10名选手ID）
│
├── 2. 发起 RPC 请求
│   └── 调用 nakama RPC "StartMatch"
│       请求体: { teamT: [...], teamCT: [...], mapId: "de_dust2" }
│
├── 3. 服务器推演
│   └── 在单个 goroutine 中顺序执行全部回合
│       生成 MatchReport 对象（包含所有事件+统计）
│
├── 4. 返回响应
│   └── JSON 格式的完整战报，~50-150 KB
│
├── 5. 客户端本地播放
│   └── 将战报存入本地状态
│       按 2 秒/条的节奏逐条渲染 HLTV 播报
│       播放过程中无需与服务器通信
```

**数据包大小预估**：
- 单场比赛完整战报: ~50-150 KB（JSON）
- 平均 ~80 KB，含 20-30 个回合的全部事件和统计

### 9.4 后续版本演进

当加入教练技能、实时决策等互动玩法后，将迁移到 Match Handler 实时模式：

| 阶段 | 通信方式 | 适用场景 |
|------|---------|---------|
| MVP | RPC 一次请求/响应 | 全自动推演，无互动 |
| v2 | Match Handler + WebSocket | 教练技能、实时路线选择 |
| v2+ | Match Handler + 观战 | 第三方实时观战 |

### 12.2 选手数据来源与存储方案

#### 12.2.1 选手属性配置 —— Excel 配表（Luban）

**所有选手的静态属性数据均存储在 Excel 配表中**，通过 Luban 导表工具生成 Go 代码和 JSON 数据，服务器启动时加载到内存。这是策划配置的一部分，不写入 Nakama 数据库。

**配表路径**: `configs/Datas/tb_player.xlsx`
**导表输出**:
- Go 结构体: `server/config/tbplayer.go`
- JSON 数据: `server/config/data/tbplayer.json` (embed 编译进 .so)

服务器在 `InitModule()` 中通过 `cfg.Init()` 加载此表到内存，推演时直接从内存读取选手属性，无需查询数据库。

#### 12.2.2 玩家拥有的选手列表 —— Nakama Storage（可选）

玩家在游戏中通过抽卡等方式"获得"了哪些选手，这个数据需要用 Nakama Storage 记录：

**Collection**: `player_inventory`
**Key**: 选手ID（如 `player_niko`）
**PermissionRead**: 1（仅自己可读）
**PermissionWrite**: 0（仅服务器可写）

```json
// Storage Value 结构（单名选手的拥有记录）
{
  "player_id": "player_niko",
  "obtained_at": "2026-07-01T12:00:00Z",
  "star_level": 1,
  "match_count": 15
}
```

> MVP 阶段若未实现抽卡系统，可暂时跳过此表，客户端直接传递阵容即可。

#### 12.2.3 玩家上阵阵容 —— 请求体传递（MVP）

MVP 阶段不存储"当前上阵阵容"到 Nakama Storage。阵容信息由**客户端在 `StartMatch` 请求体中直接传递**。

```
开战请求体:
├── team_t[]  : 5名T方选手的 player_id 列表
├── team_ct[] : 5名CT方选手的 player_id 列表
└── map_id    : 地图ID

服务器收到后:
├── 用 player_id 从 Luban 配表 (cfg) 中读取选手完整属性
├── 无需查询数据库/Storage
└── 直接开始推演
```

后续版本（含抽卡和阵容保存功能）可再加入阵容持久化存储。

### 12.3 Nakama 通讯协议规范

#### 12.3.1 通讯方式

MVP 阶段使用 **Nakama RPC（HTTP POST）** 进行前后端通信，不使用 Match Handler / WebSocket。

```
客户端发起:
  POST /v2/rpc/StartMatch?http_key=<key>
  Headers: Authorization: Bearer <session_token>
  Body: JSON payload

服务器响应:
  HTTP 200
  Body: JSON payload（完整战报）
```

#### 12.3.2 请求协议：`StartMatch`

**请求头**：

| Header | 值 | 说明 |
|--------|------|------|
| Content-Type | application/json | 固定 |

#### 12.3.4 错误响应

```go
// 服务器返回的错误格式（HTTP 非200或payload中error）
type MatchError struct {
    Code    string `json:"code"`    // 错误码
    Message string `json:"message"` // 用户可读的错误信息
}
```

| 错误码 | HTTP状态 | 说明 |
|--------|---------|------|
| `INVALID_LINEUP` | 400 | 阵容格式错误或选手不存在 |
| `DUPLICATE_PLAYER` | 400 | 同一选手在双方阵容中重复出现 |
| `LINEUP_TOO_SHORT` | 400 | 阵容选手数量不足5人 |
| `INVALID_MAP` | 400 | 不支持的地图ID |
| `SIMULATION_ERROR` | 500 | 服务器推演内部错误 |
| `RATE_LIMITED` | 429 | 请求过于频繁 |

#### 12.3.6 与现有 Nakama 架构的衔接

```
┌──────────────────────────────────────────────────────────┐
│                  Nakama 容器 (Docker)                     │
│                                                          │
│  ┌─────────────────────────────────────────────────────┐ │
│  │          Go Plugin (backend.so)                      │ │
│  │                                                      │ │
│  │  InitModule()                                        │ │
│  │   ├── cfg.Init()  ← 加载 Luban 配置表               │ │
│  │   │     ├── tb_route.json     (路线配置)             │ │
│  │   │     ├── tb_player.json    (选手属性)             │ │
│  │   │     ├── tb_weapon.json    (武器配置)             │ │
│  │   │     └── tb_combat_const.json (战斗常数)          │ │
│  │   │                                                  │ │
│  │   └── RegisterRpc("StartMatch", startMatchRPC)       │ │
│  │        │                                             │ │
│  │        ▼                                             │ │
│  │   startMatchRPC()                                    │ │
│  │   ├── 解析请求体 (TeamT, TeamCT, MapID)               │ │
│  │   ├── 校验阵容                                       │ │
│  │   ├── 加载选手属性 (从 cfg + Luban 缓存)              │ │
│  │   ├── MatchEngine.Simulate()  ← 核心推演引擎          │ │
│  │   │     ├── 逐回合演算                                │ │
│  │   │     ├── 生成事件列表                              │ │
│  │   │     └── 计算统计                                  │ │
│  │   ├── 生成 MatchReport JSON                          │ │
│  │   └── 返回响应                                       │ │
│  └─────────────────────────────────────────────────────┘ │
│                                                          │
│  ┌─────────────────────────────────────────────────────┐ │
│  │         Luban 配置表 (编译时 embed)                  │ │
│  │   configs/Datas/*.xlsx ──► Luban ──► *.json         │ │
│  └─────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────┘
```

**关键设计点**：
- RPC 函数 `startMatchRPC` 是同步执行的，整个推演在单个 HTTP 请求内完成
- 推演耗时预估：10-50ms（纯计算，无IO），对 Nakama 无性能压力
- Luban 配置表通过 `//go:embed` 编译进 `.so`，零运行时文件依赖
- 选手的"拥有数据"（Storage）在 RPC 中按需读取，用于校验和记录战绩
