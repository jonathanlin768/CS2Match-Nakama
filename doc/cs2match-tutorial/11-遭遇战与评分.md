# 11 · 遭遇战：从接触到评分

> 战斗是这套引擎的心脏。这篇回答：两个队员在 A 大互相看见之后，"开打"这件事在引擎里长什么样？以及那套著名的评分公式——它到底决定了什么，又**刻意不决定**什么。
>
> 前置依赖：09（地图）、10（决策）。

## 1. Encounter 是什么

`Encounter`（遭遇战）= 一次**有明确参战人员、地点、场景**的局部战斗。它是团战的最小单元——不拆 1v1 单挑，一次 A 大交火就是一个 Encounter（设计文档 2.5："局部交火不拆成单挑，使用小队团战模型"）。

一次 Encounter 的一生只有三个阶段：

```text
① 构建候选（谁打谁、在哪打、什么场景）
② StartEncounter：锁人 + 算分 + 安排未来脉冲
③ 脉冲逐个结算 → EncounterShouldEnd → EndEncounter
```

第 ③ 阶段的脉冲结算（伤害、死亡）是下一篇的主角，这篇讲 ① ② 和评分。

## 2. 接触：候选怎么产生

第 9 篇说过，生产中的接触来自 `discoverEncounters`（`round_engine.go#discoverEncounters`）：扫描 T×CT 组合，`playersInContact`（同节点或配置可见）就生成候选。候选构建在 `encounter.go#BuildEncounterCandidate`：

1. **过滤参战者**：存活、未在别的遭遇战中、行动状态允许参战（`actionCanEnterEncounter`：Idle/Moving/Holding/Planting/Defusing 都可以——**正在下包的人会被拉进战斗**，这正是"下包被打断"的机制来源）。
2. **必须有双方**：只有 T 或只有 CT 的候选直接 `INVALID_ENCOUNTER`。
3. **威胁分排序**：每人一个 `ThreatScore` = `(Firepower + Aim + Reaction + Awareness)/4 + HP/10 + 暴露修正`（`encounterThreatScore`）。在边上 +20、移动中 +15、架点 −10（`playerExposure`）。
4. **身份哈希**：`EncounterID = stableObjectID("enc", 回合种子, 来源行动, 场景, 节点, 排序后成员ID)`——确定性 ID，第 8 篇讲过为什么。

如果同一时刻出现多个候选（A 大和 B 洞同时开打），`ArbitrateEncounterCandidates`（`encounter.go#ArbitrateEncounterCandidates`）按 PriorityScore 从高到低贪心接受**不共享选手、不共享节点**的候选——同一名选手同一时刻只能属于一场遭遇战，但不同区域的战斗可以并行。

## 3. StartEncounter：锁人、算分、排脉冲

`StartEncounter`（`encounter.go#StartEncounter`）是这个文件最重要的函数，做了五件事：

**① 定时长**：`duration = clamp(scenario.BaseTimeCost, MinCombatDuration, MaxCombatDuration)`——近点遭遇短、多人强攻长，全靠场景配置（第 4 篇的 `#Scenario.base_time_cost`）。

**② 消耗道具**：双方各支付一次 `UtilityOpeningInitiative` 预算（单次成本约预算的 1/5，`spendScopedUtility` 的 divisor=5；预算见底会留下 `LOW_UTILITY` 原因记录，第 12 篇详述）。

**③ 算分定主动权**：`CalculateEncounterScorePair`（见第 4 节）。分数高的一方拿到 `InitiativeSide`（主动权方），初始姿态是 `Engaged`，另一方 `Holding`（`initialEncounterPosture`）。**如果分差达到 `DecisiveScoreGap`，时长减 1 秒**——强队打这场架更快结束，这是 EncounterScore 影响战局的少数方式之一。

**④ 锁人**：对每个参战者——取消当前行动（移动/下包被打断）、`Version++`、状态置 `Engaged`、`BusyUntil = EndsAt`、记录 `EngagementID`。第 8 篇的版本失效机制在这里被调用，这就是"交火打断一切"的实现。

**⑤ 排脉冲**：`pulseCount = clamp(ceil(duration / PulseFireWindow), 1, MaxEncounterPulses)`，每个脉冲安排在 `ceil(duration×i/pulseCount)`（至少间隔 1 秒，不超 `EndsAt`），优先级 100；最后排一个 `ActionCombatEnd`（优先级 50）。**StartEncounter 不生成任何伤亡**——测试 `TestEncounterStartOnlySchedulesFuturePulsesAndDoesNotBlockOtherActions` 就断言这一点：它只是预约了未来几次"开枪窗口"和一次"散场"。

> ⚠️ **设计 vs 现实提示**：`StartEncounter` 打断移动用的是 `cancelCurrentAction`（第 8 篇），而不是 `movement.go#InterruptMovementForEncounter`——后者（含边上进度推进）在生产中没有调用者，是第 15 篇 Q3 断链的一部分。

## 4. 三层评分：个人 → 团队 → 遭遇战

战斗评分分三层，逐层递进，**每层用途不同，绝不混用**（设计文档 2.5 反复强调的唯一公式原则）：

### 4.1 第一层：WeightedPlayerScore（场景加权基础分）

`combat.go#WeightedScenarioPlayerScore`：场景族定义了十属性权重（`EncounterModifier` 里 `Factor=ScenarioWeight` 的行，权重合计必须 = 100，第 4 篇校验过），个人基础分 = 十属性加权和 / 100。**同一名选手在 A 大长枪局和 B 洞贴脸局的价值完全不同**——这就是"场景决定哪些属性重要"的落地。

### 4.2 第二层：PlayerCombatScore（个人战斗分）

`combat.go#CalculatePlayerCombatScore`：

```text
PlayerCombatScore =
    WeightedPlayerScore
  + RoleTagModifier    （Entry 在 SiteEntry 场景 +5；Support +2）
  + WeaponModifier     （(武器伤害−30)/2 + 射速/600）
  + PostureModifier    （Holding +6 / Engaged +3 / Moving −5 / Retaking +2，再叠配置修正）
  + VisibilityModifier （在边上 −4，再叠场景 MapTag/修正）
  + TeamSupportModifier（协同分 + 配置支援修正）
  − StaminaPenalty     （(MaxStamina − 当前体能) / 10）
  − DamagePenalty      （(MaxHP − 当前HP) / 10）
  − SuppressionPenalty （被压制 −8）
```

配套的 `defaultCombatModifiers`（`combat.go#defaultCombatModifiers`）负责生产默认修正，其中"在边上 −4""压制 −8"这类数值是**写死在代码里的尺度**——这正是第 15 篇 Q7 要讨论的"隐藏平衡常量"。

### 4.3 第三层：EncounterScore（团队遭遇分）

`combat.go#CalculateEncounterScorePair` 对双方各算一个：

```text
DeterministicEncounterScore =
    Σ PlayerCombatScore（本方参战者）
  + TeamModifier        （协同五项合计，见下）
  + ScenarioModifier    （scenario.BaseWeight / 5）
  + UtilityModifier     （道具修正，一次性；OpeningInitiative 基准 8、其余类型 0.2）
  + MomentumModifier    （队伍气势 / 10）
  + TimePressureModifier（剩余时间 < 强攻阈值时：T 加压、CT 减分，最多 ±5）

FinalScore = Deterministic + BoundedRandomNoise
```

协同五项（`combat.go#CalculateCoordination`）是"补枪概率高一点"的具体实现（设计文档 2.5）：

| 项 | 触发 | 值 |
|----|------|-----|
| TradeCoverage（补枪覆盖） | 队友 ≥2 人 | (人数−1)×2 |
| Spacing（站位间距） | 不同位置数 | (位置数−1)×1.5 |
| Crossfire（交叉火力） | ≥2 个位置 | 位置数×2 |
| SyncPeek（同步拉枪） | ≥2 人移动/交火姿态 | 人数×1.5 |
| Isolation（脱节） | 只剩 1 人 | −6 |

`TeamModifier = Trade + Spacing + Crossfire + SyncPeek − Isolation`。孤立无援的选手先扣 6 分——这就是"落单必死"的数值表达。

### 4.4 EncounterScore 到底决定什么？

**这是最容易误解的一点**。EncounterScore 的作用仅限于（`encounter.go#StartEncounter` + 设计文档 2.5）：

1. 主动权归属 → 初始姿态（Engaged vs Holding）；
2. 时长修正（分差悬殊时减 1 秒）；
3. 脉冲数与时间安排的背景；
4. 战报解释（Reason 链）。

**它不决定谁赢、不决定击杀数、不预设伤亡表**。伤害和死亡完全由每个脉冲内的独立采样产生（第 12 篇）。`protectEncounterTrend`（`combat.go#protectEncounterTrend`）只做一件事：确定性分差 ≥ `DecisiveScoreGap` 时，把噪声钳制在"翻不了盘"的范围——**保护趋势，不锁定结果**。设计文档的原话：强势方更稳定，"但仍允许实际概率链产生爆冷"。

## 5. 生存分：被攻击者的另一半公式

攻击方有战斗分，被攻击方有生存分（`combat.go#CalculateTargetSurvivalScore`）：

```text
TargetSurvivalScore =
    Positioning + Reaction
  + CoverModifier     （架点 +8）
  + TeamSupportModifier（协同合计）
  + Focus             （当前专注值）
  − MovementExposure  （在边上或移动中 −10）
  − DamagePenalty     （(MaxHP−HP)/10）
```

两个公式在 `ResolveAttackWindow` 里相遇：`sigmoid((CombatScore − SurvivalScore) / CombatScale)` 得到命中率——下一篇把它走完。

## 6. 散场：EndEncounter 与控制权

遭遇战结束有三种方式（`combat.go#EncounterShouldEnd`）：一方局部全灭、脉冲打满、时长到点。`EndEncounter`（`encounter.go#EndEncounter`）收尾时做两件大事：

1. **控制权结算**：存活方夺得该节点的 `ActualControl`，`ResolveContest`（`round_state.go#ResolveContest`）同时给**参战双方**写入各自的 `KnownControl`（带 TTL）。这就是第 7 篇"Actual vs Known"分离的生产入口——**控制权情报是从战斗里长出来的**。若控制权真的变了，生成 `CONTROL_GAINED` 事件（优先级 40）。
2. **释放选手**：`Version++`、清 `EngagementID`、姿态回 `Default`。释放后的选手由 `ensureActions` 重新接管（第 6 篇），同时 `EncounterEnd` 会触发一次决策重评估（第 10 篇的指纹差分）。

## 本篇回顾

- Encounter = 局部团战单元：构建候选 → 锁人算分排脉冲 → 脉冲结算 → 散场。
- StartEncounter 只预约未来，不预生成伤亡；同秒多候选按"不共享选手/节点"仲裁并行。
- 三层评分：场景加权基础分 → 个人战斗分（九项）→ 团队遭遇分（含协同五项）。
- EncounterScore 只决定主动权/时长/解释，**不决定胜负**；保护趋势 ≠ 锁定结果。
- 生存分与战斗分的差进入 sigmoid，是下一篇的起点。
- EndEncounter 是控制权情报的生产入口。
