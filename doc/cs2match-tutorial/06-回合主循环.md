# 06 · 回合主循环：离散事件状态机

> 这是内核区的第一篇，也是整个专栏的"分水岭"。这篇讲清楚 `runCausalRound` 的每一次循环在做什么，之后的状态、行动、战斗、炸弹，全部是这片循环里的零件。
>
> 前置依赖：05（整场编排）。

## 1. 先建立心智模型：不是"逐秒"，是"跳事件"

90 秒的回合，逐秒模拟要 90 次循环，而事件之间的大段时间里其实**什么都没发生**。离散事件状态机的做法是：每个行动在生成时就把自己的完成时刻冻结为绝对时间 `ResolveAt`，然后循环只做一件事——

```text
跳到下一个最早到期的事件 → 结算 → 根据新状态生成新行动 → 再跳
```

一场典型回合只有几十个"有意义的瞬间"。第 1 篇说过，这样做的最大收益不是性能，而是**战报天然可解释**：每个事件都有精确时间戳，事件之间明确"无事发生"。

## 2. 回合的四个阶段

`runCausalRound`（`round_engine.go#runCausalRound`）可以切成四段：

**① 开局准备（一次）**：

```go
tSelection := SelectStrategyTemplate(...)   // T 选战术模板
ctSelection := SelectCTSetup(...)           // CT 选防守 setup（独立种子！）
plan := BuildRoundPlan(...)                 // 角色、路线、持包人
state := NewRoundState(input, plan)         // 权威状态初始化
DeployOpeningActions(state)                 // 部署开局 Move/Hold
```

注意 `SelectCTSetup` 的调用里**没有 T 模板参数**——CT 不能偷看 T 的战术（信息边界，第 10 篇展开）。部署完成后进入主循环，此时 `state.Terminal == nil`（终局为空）。

**② 主循环（直到终局出现）**，每轮做五件事：

```go
for state.Terminal == nil {
    state.RecordTransition()                              // 状态转换计数（防死循环）
    beforeState := StateFingerprint(state)                // 状态指纹（无进展检测）
    runtime.ensureActions()                               // ① 补行动
    runtime.reevaluatePhase()                             // ② 投影阶段
    terminal := EvaluateRoundTerminal(state, ...)         // ③ 判终局
    if terminal != nil { enterRoundEnd(terminal); break }

    nextAt, kind := state.NextTime()                      // ④ 选下一个时间点
    state.AdvanceTimeline(nextAt)
    batch, sourceID := runtime.resolveTimestamp(kind)     // ⑤ 结算同时间戳批次
    DecayIntelAndControl(...)                             // 情报/控制权衰减
    DetectDecisionTriggers(...) → scheduleDecisions()     // 决策触发
    runtime.reevaluatePhase()
    terminal := EvaluateRoundTerminal(state, batch)       // 批次后再判一次
    ObserveStateProgress(state, beforeState, sourceID)    // 无进展计数/恢复周期
}
```

**③ 收尾**：`ProjectRoundResult` 投影出战报（第 13 篇），返回 `RoundSimulationResult{Round, Terminal}`。

## 3. 逐块拆解主循环

### 3.1 ensureActions：唯一合法的"行动补给站"

`round_engine.go#ensureActions` 按优先级补充行动，每个分支"启动了一个就返回"：

```go
discoverEncounters()       // 最高优先：双方有接触就开打
if Bomb.Planting/Defusing { return }   // 正在下包/拆包时安静等待
if 已下包 { ensurePostPlantActions() }  // 回防移动 / 自动拆包
else     { ensurePrePlantActions() }    // 救包 / 自动下包 / 沿路线推进
scheduleDecisions()        // 最后：中期决策
```

两个值得品味的细节：

- **自动下包**（`ensurePrePlantActions`）：持包 T 站在包点、包点不是 CT 控制/争夺中、且没有可见 CT 威胁时，引擎自动 `StartPlantAction`——这就是"AI 不是脚本，但也不需要玩家输入"的体现。
- **路线推进**：空闲队员沿着 `Plan.OpeningRoutes` 的路线节点序列走到下一个节点（`nextRouteNode`）；CT 用 `CTSetupTemplateID` 的模板节奏。走到哪一步了由位置决定，不是剧本。

### 3.2 NextTime：跳到哪一刻？

`scheduler.go#NextTime` 从多个候选里选**最小的未来时间点**，并带上"为什么"（`NextTimeKind`）：

| 候选 | 条件 |
|------|------|
| 队首行动的 `ResolveAt` | 队列非空 |
| `BombDeadline`（爆炸时刻） | 炸弹已下包/拆包中 |
| `RoundDeadline - ForceExecuteThreshold` | 下包前——这是**强攻决策**的预警线（剩 60s） |
| `RoundDeadline` | 下包前——回合结束线 |
| 情报/控制权记录的 `ExpiresAt` | 有情报（当前版本恒空，见 15 篇） |

主循环里有个防御性检查（`round_engine.go#runCausalRound`）：

```go
if ready, ok := state.Scheduler.Peek(); ok && ready.ResolveAt <= state.Timeline {
    nextAt, kind = state.Timeline, NextTimeAction   // 有到期行动被漏掉？立即结算
}
```

这是对"跳过头"的保护：如果队首行动已经到期却还没结算，就把时间点拉回当前时刻。

**如果所有候选都没有**（队列空、无 deadline）——这就是"卡死"信号：先 `RecordNoOp` + `ScheduleNoProgressRecovery` 尝试一次确定性恢复，还不行就返回 `SCHEDULER_STALLED` 错误，而不是随便判谁赢（第 13 篇展开 NoProgress 机制）。

### 3.3 resolveTimestamp：同时间戳的批次结算

时间推进后，`resolveTimestamp`（`round_engine.go#resolveTimestamp`）把所有 `ResolveAt == Timeline` 的行动**依次弹出结算**：

```go
for {
    action, ok := state.Scheduler.Peek()
    if !ok || action.ResolveAt > state.Timeline { break }
    validActors := validActionActors(state, action)          // ① 行动资格校验
    if len(validActors) < maxInt(1, action.MinRequiredActors) {
        cancelActionForActors(state, action); continue       // ② 不够人 → 整组取消
    }
    applied := runtime.resolveAction(action, validActors)    // ③ 按类型分发给 resolver
    batch.Effects = append(...); batch.Events = append(...)  // ④ 汇入本批
}
```

行动类型分发（`resolveAction`）是个大 switch：移动到达 `CompleteMovement`、拦截检查 `ResolveInterceptCheck`、战斗脉冲 `ResolveCombatPulse`、决策 `ResolveDecision`、下包/拾包/拆包/爆炸各自的 `Resolve*`……一个行动类型对应一个 resolver，职责清晰。

> ⚠️ **设计 vs 现实提示**：设计文档要求"同时间戳批次使用批次开始快照原子结算"（`design.md#Decisions 6`），但当前实现是**逐行动顺序结算**——同秒的第二个行动能看到第一个行动的结果。战斗脉冲内部的原子性已经实现（第 12 篇），但**跨行动的批次原子性还没有**。这是 Review 指南问题清单 Q1（第 15 篇汇总）。

### 3.4 终局判定：为什么判两次？

主循环里 `EvaluateRoundTerminal` 出现了**两次**：循环顶部（行动补充后）和批次结算后。为什么？

- **循环顶部那一次**：处理"无事发生但已经满足终局"的情形（比如时间耗尽时队列恰好是空的）。
- **批次后那一次**：真正的终局来源——击杀导致 T 全灭、爆炸倒计时归零、拆包完成……都发生在结算之后。

终局纯函数只读状态，不写任何东西（第 13 篇展开）。一旦返回非空，`enterRoundEnd`（`round_engine.go#enterRoundEnd`）做三件事：**取消所有存活玩家的行动**（死者不再行动，活者也停下）、清空调度队列、生成 `ROUND_END` 事件并跑 `ValidateTerminalInvariants` 最终不变量校验。

## 4. Phase：解释性投影，不是全局锁

`reevaluatePhase`（`round_engine.go#reevaluatePhase`）每轮把主导活动投影成一个阶段标签：

```go
switch {
case Terminal != nil:              phase = RoundEnd
case Bomb == Planted/Defusing/...: phase = PostPlant
case Bomb == Planting:             phase = Planting
case len(ActiveEngagements) > 0:   phase = Clash
case 持包者在包点:                  phase = SiteContest
case 队列里有决策行动:              phase = Rotate
case Timeline == 0:                phase = OpeningDeploy
default:                           phase = Advance
}
```

设计文档强调（`doc/simuMatchDesign.md#3.4`）：**Phase 只是"主导活动"的投影，不是排他性全局锁**。A 大在 `Clash` 的同时，B 区的队员照样可以完成移动、进点、下包。真正的并发由"行动是否共享 Actor"来决定（第 8 篇）。`PhaseHistory` 记录了回合的完整阶段轨迹，最终进战报。

## 5. 防死循环的四道保险

主循环自带四条硬保险（全部来自必配常量，第 4 篇）：

| 保险 | 触发后 |
|------|--------|
| `MaxStateTransitions`（200） | 循环次数超限 → `STATE_TRANSITION_LIMIT_EXCEEDED` |
| `MaxScheduledActions`（1500） | 队列超限 → `SCHEDULER_LIMIT_EXCEEDED` |
| `MaxRoundTimeline` | 时间超上限 → `TIMELINE_LIMIT_EXCEEDED` |
| NoOp 检测 + 恢复周期 | 连续无进展 → 恢复尝试 → 仍失败 → `no_progress_timeout` 终局 |

第 3 条和"不猜胜方"原则呼应：超时返回**错误**，而不是按当前局势判谁赢——模拟器宁可失败也不编造结果。

## 本篇回顾

- 回合 = 一次开局准备 + "跳事件→结算→补行动→判终局"循环 + 投影收尾。
- `ensureActions` 是行动补给站：遭遇战 > 下包/拆包安静期 > 回防 > 推进 > 决策。
- `NextTime` 从行动/炸弹/回合/强攻/情报五类 deadline 里选最早者。
- 终局判两次：循环顶（空队列兜底）和批次后（真终局来源）。
- Phase 是投影不是锁；四道硬保险保证循环必终止、绝不猜胜方。
