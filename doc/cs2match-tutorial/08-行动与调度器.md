# 08 · 行动生命周期与调度器

> 这篇讲引擎的"神经系统"：行动（Action）如何被创建、互斥、打断、失效，以及确定性调度器如何保证 1000 个行动也能排出唯一的结算顺序。
>
> 前置依赖：06（主循环）、07（权威状态）。

## 1. 行动三层模型：Intent / Action / Busy

设计文档把"行动"拆成三层（`doc/simuMatchDesign.md#3.3`），对应三个不同的生命周期：

| 层 | 结构 | 生命周期 | 例子 |
|----|------|---------|------|
| **Intent（意图）** | `action.go#Intent` | 持续，直到被新意图替换 | "我要去 B 包点下包" |
| **ActionInstance（行动）** | `action.go#ScheduledAction` | 一次执行，可被打断 | "从 B_UPPER 移动到 B_SITE" |
| **BusyInterval（占用）** | `action.go#BusyInterval` | 时间区间，表达互斥 | "0:30–0:36 我都在移动" |

核心规则：**Intent 可以活很久，Action 是一次性的，Busy 管互斥**。交火打断了你的移动 Action，你的 Intent（去 B）还在——交火结束后 planner 重新评分，可能恢复移动，也可能改主意转点。旧 Action 绝不自动复活。

`ScheduledAction` 的关键字段（`action.go#ScheduledAction`）：

```go
type ScheduledAction struct {
    ID                string
    ParentActionID    string   // 子行动指向父行动（如 Pulse 属于某次 Encounter）
    Type              ActionType
    ActorIDs          []string // 参与选手（构造时排序冻结）
    StartAt / ResolveAt int     // 开始/完成绝对时刻
    Priority          int       // 同秒优先级
    VersionByActor    map[string]int  // 每个选手的版本快照
    MinRequiredActors int       // 组行动的最少存活人数
    Payload           ActionPayload   // 类型专属数据
}
```

行动类型全集（`action.go` 的 `ActionType` 常量）：`MoveStart/MovementArrive/InterceptCheck/HoldStart/EncounterStart/CombatPulse/CombatEnd/DecisionResolve/PlantStart/PlantComplete/PickupComplete/DefuseStart/DefuseComplete/BombExplode/RoundExpire/IntelDecay/ControlDecay`。第 6 篇的 `resolveAction` switch 就是按这个清单分发的。

## 2. 互斥与版本失效：防"幽灵完成"

CS 里最典型的并发问题是：**选手 5 秒前开始下包，3 秒后被击杀，2 秒后"下包完成"事件却照样触发**。引擎用两个机制解决：

### 2.1 独占行动

`BeginExclusiveAction`（`scheduler.go#BeginExclusiveAction`）在行动开始时对每个 Actor 做三件事：`Version++`、记录 `CurrentActionID`、写入 `BusyInterval`。同一选手同时只能有一个行动——想开新行动？旧行动必须先被显式取消或完成。

### 2.2 结算前四重校验

行动到期结算时，`validActionActors`（`scheduler.go#validActionActors`）逐选手校验：

```go
player.Alive                                  // ① 还活着
player.Action.CurrentActionID == expectedID   // ② 还在做这个行动
player.Action.Version == action.VersionByActor[actorID]  // ③ 版本没变过
locationMatchesAction(...)                    // ④ 位置还在行动起点
```

**版本号**是灵魂：任何打断（死亡、交火锁定、转点重规划、开始下包）都会 `Version++`。旧行动持有的版本快照瞬间作废，结算时静默丢弃——**不产生完成事件，也不退还已消耗的时间/体能**。设计文档说得很直白：这是为了防止"打断后残留幽灵完成事件"（`design.md#Decisions 4`）。

### 2.3 组行动与 MinRequiredActors

多人行动（如三人同步拉枪）构造时冻结两样东西：排序后的 `ActorIDs` 和 `MinRequiredActors`（从来源路线/模板的人数约束派生，单人行动为 1）。结算时：

- 失效成员先从资格集合里剔除；
- **剩余合法人数 ≥ MinRequiredActors** → 剩余成员继续；
- 不够 → 整个行动取消，幸存成员重新规划。

规则没有第二阈值、没有随机重roll——"继续还是取消"完全由冻结的人数和当前存活数决定（`round_engine.go#resolveTimestamp` 里的判断）。

## 3. 确定性调度器：堆 + 五键排序

`ActionScheduler`（`scheduler.go#ActionScheduler`）内部是一个 Go 标准库 `container/heap` 的最小堆。比较器 `Less`（`scheduler.go#scheduledActionHeap.Less`）定义了**唯一结算顺序**：

```text
ResolveAt 升序（谁先到期谁先结算）
→ Priority 降序（同秒时战斗伤害 > 掉包 > 下包…）
→ ActionType 升序（字典序）
→ MinActorID 升序
→ ActionID 升序（最终决胜，ID 本身是哈希，稳定）
```

为什么这样设计？**因为 map 遍历顺序在 Go 里是随机的**。如果哪天代码里 `for k, v := range map` 之后直接 push 进堆，两场同 seed 的比赛可能产生不同的结算顺序，进而产生不同的结果。五键排序保证：**无论行动以什么顺序入队，弹出顺序唯一**。`scheduler_test.go#TestSchedulerHeapIsDeterministicAcrossInsertionOrder` 就是专门守护这一点的测试。

`Schedule`（`scheduler.go#Schedule`）入队时还做了防御：ID/时间合法性检查、`MaxScheduledActions` 上限、以及把 `ActorIDs`/`VersionByActor`/`ParticipantIDs` **深拷贝排序**后再入堆——防止调用方后续修改切片污染队列。

## 4. 同秒优先级：一张表管所有"先后"

`ResolveAt` 相同的行动，靠 `Priority` 字段定先后。完整数值表（分布在 `effect_apply.go` 与 `bomb.go` 的常量）：

| 优先级 | 行动/效果 | 为什么 |
|---:|---|---|
| 100 | `CombatPulseCommit`（脉冲伤害提交） | 伤害与死亡必须先落 |
| 90 | `CombatAftermath`（战斗后效） | 压制/气势在死亡之后 |
| 80 | `BombDrop`（掉包） | 死亡 → 掉包 → 下包完成 |
| 70 | `PlantComplete`（下包完成） | 击杀先于下包完成（同秒击杀者 → 下包失败） |
| 60 | `DefuseComplete`（拆包完成） | 拆包先于爆炸 |
| 50 | `BombExplode`（爆炸） | "拆包完成 == 爆炸时刻"判 CT 赢 |
| 40 | 控制权变化 | 战斗后更新占领 |
| 30 | `HoldStart` | 防御性站位 |
| 20 | `MovementArrive`/`DecisionResolve` | 移动到达、决策 |
| 10 | `IntelDecay` | 情报衰减收尾 |

两个经典同秒边界（都是测试用例名，见 `bomb_test.go`）：

- 击杀持包者与下包完成同秒 → 脉冲(100)先于下包(70)，下包失败、炸弹掉落；
- 拆包完成与爆炸同秒 → 拆包(60)先于爆炸(50)，**CT 赢**。设计文档明文："等号判给 CT"（`doc/simuMatchDesign.md#2.7`）。

## 5. 时间推进与硬限制

`AdvanceTimeline`（`scheduler.go#AdvanceTimeline`）是**时间只能向前**的唯一入口：

```go
if at < s.Timeline { return INVALID_TIMELINE }                    // 禁止倒流
if at > s.constants.Int("MaxRoundTimeline", 0) { return TIMELINE_LIMIT_EXCEEDED }
s.Timeline = at
```

`RecordTransition`（`scheduler.go#RecordTransition`）在主循环每轮开头计数，超 `MaxStateTransitions` 直接报错。这两条加上 `RecordRotation`（转点次数上限），构成第 6 篇说的"四道保险"中的前两道。

## 6. ID 的确定性派生：为什么没有自增 ID

`action.go` 底部的三个工厂函数值得单独讲：

```go
NewActionID(roundSeed, actionType, intentID, startAt, resolveAt, 排序后ActorIDs, ordinal)
NewEffectID(roundSeed, actionID, effectType, ordinal)
NewEventID(roundSeed, actionID, effectID, eventType, ordinal)
```

三者都经 `stableObjectID`（`action.go#stableObjectID`）格式化成 `前缀_十六进制哈希`，哈希来自 `deriveSeed`（FNV-1a，`seed.go#deriveSeed`）。**没有全局自增计数器**——因为自增序号依赖执行顺序，同 seed 重跑如果某个分支多走一次，后续所有 ID 都会漂移。语义身份派生则保证：同一行动在任何一次运行里都叫同一个名字。`ordinal` 是局部序号，只在该行动内部稳定。

这也解释了为什么 `NewActionID` 里要把 `ActorIDs` 排序后再拼进哈希：`[P3,P1]` 和 `[P1,P3]` 必须是同一个行动的同一个 ID。

## 本篇回顾

- 三层模型：Intent 持久、Action 一次性、Busy 管互斥；打断后旧 Action 永不复活。
- 版本失效（ActorVersion）是防"幽灵完成"的核心：死亡/打断 → `Version++` → 旧行动静默作废。
- 组行动按冻结的 `MinRequiredActors` 确定性继续或取消，无第二阈值。
- 堆排序五键（时间/优先级/类型/最小ActorID/行动ID）保证结算顺序与插入顺序无关。
- 同秒优先级一张表管所有先后；ID 全部语义派生，无自增计数器。
