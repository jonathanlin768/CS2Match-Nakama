# 12 · 战斗脉冲：原子伤害与死亡

> 这是战斗内核的下半场，也是整个引擎因果性的**最高潮**：同一秒五个人互相开枪，伤害怎么算、死亡怎么定、炸弹怎么掉——每一步都必须在"不可变快照 + 原子提交"的框架里完成。
>
> 前置依赖：11（遭遇战与评分）。

## 1. 脉冲：一次遭遇战里的"射击窗口"

第 11 篇说过，StartEncounter 预约了 N 个 `CombatPulse`（N ≤ `MaxEncounterPulses`=5）。每个脉冲到点时，`combat.go#ResolveCombatPulse` 走一遍完整的"射击循环"：

```text
① 冻结快照 CreateCombatPulseSnapshot
② 每人选目标 SelectCombatTarget
③ 每人开一枪 ResolveAttackWindow（采样命中/致命/伤害）
④ 所有伤害一起原子提交 ApplyCombatPulseCommit
⑤ 战斗后效 applyCombatAftermath
⑥ 判断是否散场 EncounterShouldEnd
```

**脉冲 = 一次原子战斗事务**。设计文档的原话（`doc/simuMatchDesign.md#2.5`）：

> 某名选手在同一 pulse 中被击杀，不会取消其已经基于 pulse 快照形成的攻击。

这就是"同脉冲互换"（两人同秒互杀）在规则上合法的原因——测试 `TestCombatPulseCommitAllowsSamePulseTrade` 专门守护它。

## 2. 快照：为什么必须冻结

`CreateCombatPulseSnapshot`（`combat.go#CreateCombatPulseSnapshot`）把参战者的**当时状态**（HP、体能、专注、压制、姿态、位置、武器）和**可见性矩阵**（谁看得见谁，`VisibleTargets`）全部拷进不可变快照。

冻结的理由：如果第 3 个人开枪时读到的是"第 2 个人已经打死第 4 个人"之后的世界，射击顺序就会产生因果偏差——先开枪的人占便宜。**快照保证所有人的射击都基于同一瞬间的世界**，伤害统一提交，死亡统一派生。

`pulseSeed = deriveSeed(回合种子, "encounter", EncounterID, 脉冲序号, ResolveAt)`——每个脉冲、每对 (攻击者, 目标, 用途) 的随机数都是独立派生的（`stableUnit(pulseSeed, actorID, targetID, "hit"/"lethal"/"damage")`）。同种子重跑，每一枪的结果都逐位相同。

## 3. 目标选择：威胁分 + 平手摇号

`SelectCombatTarget`（`combat.go#SelectCombatTarget`）的排序键：

```text
ThreatScore 降序（(Firepower+Aim+Reaction+Awareness)/4）
→ Exposure 降序（边上 +20 / 移动 +15 / 架点 −10）
→ Distance 升序（越近越危险）
→ HP 升序（残血优先）
→ PlayerID 升序（最终决胜）
```

注意前四档的语义：**先打最危险、最暴露、最近、最残血的**。如果多个目标威胁分差在 `CloseScoreGap` 之内，进入"平手池"，用 `TieRoll`（种子派生的稳定摇号）选出——**接近的目标之间保留随机性，但随机性本身是确定性的**。

## 4. 一枪的数学：命中、致命、伤害

`ResolveAttackWindow`（`combat.go#ResolveAttackWindow`）是单次射击的完整采样：

### 4.1 概率链（`CalculateAttackProbabilities`）

```text
RawHit = sigmoid((CombatScore − SurvivalScore) / CombatScale)
Hit    = clamp(RawHit, MinHitChance, MaxHitChance)          // 0.05..0.95

RangeFactor  = Long→武器RangeModifier / Medium→√RangeModifier / Close→1
ArmorFactor  = 0.5 + clamp(穿甲率)×0.5（有甲时）
BaseShotDamage = 武器伤害 × RangeFactor × ArmorFactor

Burst = clamp(⌊射速/60 × PulseFireWindow⌋, 1, 弹匣)
BurstPotential = 1 + log2(Burst)×0.25
DamagePotential = clamp(BaseShotDamage × BurstPotential / MaxHP, Min, Max)

Exposure = clamp(1 + 视线.ExposureModifier/100, Min, Max)
RawKill = Hit × DamagePotential × Exposure
Kill    = clamp(min(RawKill, Hit), 0, MaxKillChance)        // 恒 ≤ Hit，上限 0.85
```

两条设计铁律在这里落地：

1. **`KillChance ≤ HitChance`**：一枪先得命中，才谈致命。`min(rawKill, hit)` 保证武器再强也超不过命中率。
2. **没有 `TargetHPFactor`**：低 HP 更容易死，**不是**靠给残血目标乘一个击杀加成，而是靠"实际伤害自然打穿剩余 HP"——测试断言禁止出现该因子（第 15 篇会再提到）。

### 4.2 三次采样（`ResolveAttackWindow`）

```text
hitRoll    >= HitChance            → Miss（EffectMiss）
lethalRoll <  KillChance/HitChance → LethalWindow（致命窗口）
damage     = max(1, round(BaseShotDamage × (0.5+damageRoll) × min(2, 1+(Burst−1)×0.08)))
LethalWindow 时：damage = max(damage, 目标当前HP)   ← 保证致死
```

`damageRoll` 让单发伤害在 0.5–1.5 倍之间波动（burst 加成最高 2 倍）；**致命窗口直接把伤害抬到至少等于目标 HP**——命中、致命、伤害三个维度独立采样，是"伤害值"与"击杀判定"两条概率链的解耦。

> ⚠️ **设计 vs 现实提示**：`0.5+damageRoll`、`(Burst−1)×0.08`、`log2(Burst)×0.25`、`(Damage−30)/2 + RPM/600` 这些尺度都是**写死在 combat.go 里的常量**，与"所有平衡数字必须在配表里"的规格有张力（Review 指南 Q7，第 15 篇）。

## 5. ApplyCombatPulseCommit：五步原子提交

所有攻击采样完毕后，伤害 Effect 集合进入 `effect_apply.go#ApplyCombatPulseCommit`。这是引擎里最值得逐行读的函数：

**第一步：校验**。行动必须是优先级 100 的 CombatPulse、时间必须等于当前 Timeline；伤害 Effect 逐个体检（来源行动、类型、时间戳、金额非负、参与者存在）；按目标分组后**预估**派生数量（死亡 + 掉包），一次性检查 `MaxEffectsPerTimestamp` 上限。

**第二步：按目标归一分配**（`allocateActualDamage`）：

```text
目标剩余 HP = 30，两个攻击者伤害 40 + 40：
实际损失 = min(30, 80) = 30
分配：A 得 15、B 得 15（比例分配，余数按伤害从高到低补齐）
```

**伤害永远不会溢出 HP**——溢出部分不产生额外效果，同时攻击者们的 `Damage` 统计按实际贡献累加。

**第三步：统一扣 HP**。所有目标的 HP 扣减在此完成，同时生成 `DAMAGE` 事件（原因里带 `player.hp` 的 Before/After 状态变化）。

**第四步：派生死亡**。扣完 HP 后扫描目标：

- `HP ≤ 0` → `Alive = false`、`Deaths++`、击杀者 `Kills++`；
- **击杀归属** `selectKillContribution`：实际贡献最高者，平手按 EffectID 字典序（确定性！）；
- `cancelCurrentAction`：死者的下包/拆包被中断（`interruptBombActionForPlayer` 生成 `PLANT_INTERRUPT`/`DEFUSE_INTERRUPT` 事件、炸弹状态机回退）；
- 生成 `KILL` 事件：`IsFirstKill`（本回合此前无击杀）、`IsTrade`（5 秒内对方杀过人）、`assist_ids`（本回合对受害者造成过伤害的其他人，`assistIDsForKill`）。

**第五步：派生掉包与打断**：

- 死者持包 → `Bomb.Drop(位置, 时间)` + `BOMB_DROP` 事件（优先级 80）；
- 受伤未死者若在移动/下包/拆包 → `interruptExternalAction`：`Version++`、行动取消（**被打中会打断下包**，这是 CS 的核心手感）。

最后：批内事件排序（第 13 篇的排序键）、追加进 `state.Events`、跑 `ClampAndValidate` 不变量体检。

## 6. 后效：Aftermath 与 Momentum

伤害提交后，`applyCombatAftermath`（`combat.go#applyCombatAftermath`）处理"战斗的余波"：

| 对象 | 效果 |
|------|------|
| 每个开枪者 | Focus −2、Stamina −2（clamp 到下限）、姿态转 `Engaged` |
| 每个被命中者 | Focus −8、`Suppressed = true`、姿态转 `Holding` |
| 每个 KILL | 击杀方 Momentum +5、被击杀方 −5（clamp ±100） |

`Suppressed` 标记会让目标下一脉冲的 `PlayerCombatScore` 吃 −8 压制惩罚（第 11 篇的 `SuppressionPenalty`）——**被压制的枪打不中人**，这是引擎里闭环的数值链。Momentum 则流入下一脉冲的 `EncounterScore`（`Momentum/10`），首杀滚起的雪球就这样一层层传下去。

## 7. Utility 预算：道具为什么不是无敌光环

设计文档给 Utility 划了硬边界（`doc/simuMatchDesign.md#2.4`）：**道具是执行能力，不是全局战力光环**。实现（`utility.go`）：

- 每队每回合一个 `UtilityBudget`，`InitializeUtilityBudget` 在开局按模板初始化，公式（`utility.go#InitializeUtilityBudget`）：

```text
budget = cap × (0.35 + 0.35×平均Utility/100 + 0.2×min(1, 道具数/人数/4) + 0.02×Support人数)
模板含 Support 角色再加 5%，clamp 到 [0, cap]
```

- 六类用途：`VisibilitySuppression / OpeningInitiative / ExposureReduction / SyncPeekQuality / PlantCover / DefuseCover`（`utility.go` 的 `UtilityEffectType`）；
- `SpendUtility` 扣预算（Support 人数带来效率折扣 `1 + 0.15×supportCount`），**扣不动就留下 `LOW_UTILITY` 原因**（不报错、不生效）——第 11 篇的 `spendScopedUtility`（遭遇战开局主动性，单次成本约预算的 1/5）和下包/拆包的掩护消耗（第 13 篇）都走这里；
- `ScopedUtilityModifier` 把"当前还生效的道具窗口"折算成分数，修正值 = `utilityBaseModifier(类型) × (0.5 + 平均Utility/200)`；`OpeningInitiative` 的基准是 **8**、其余类型 0.2——只作用于局部战斗，不跨战场复用。

预算耗尽后，道具修正归零但战斗照常进行——这正是"Utility 不无限生效"的数值表达。

## 本篇回顾

- 脉冲 = 快照冻结 → 目标选择 → 独立采样 → 原子提交 → 后效 → 散场判断。
- 所有射击基于同一快照：同脉冲互换合法，先开枪不占因果便宜。
- 概率链：sigmoid 命中 → 伤害包 → `KillChance ≤ HitChance`，无 TargetHPFactor。
- 伤害按实际 HP 归一分配，击杀归属贡献最高者（平手按 ID）。
- 死亡派生顺序：扣 HP → 死亡 → 击杀归属 → 打断下包/拆包 → 掉包。
- 后效闭环：Suppressed → 下脉冲 −8；Momentum → EncounterScore。
