# 05 · 整场编排：MR12、换边与加时

> 这一篇讲"回合之上"的那层：24 个常规回合怎么循环、半场怎么换边、打平怎么进加时，以及整套系统里最容易被写错的三个字——**比分权威性**。
>
> 前置依赖：03（端到端旅程）。

## 1. 三层结构：谁管什么

整场比赛的组织分三层，各司其职：

| 层 | 文件 | 职责 |
|----|------|------|
| 比赛编排 | `engine.go#simulateMatch` | 回合循环、换边触发、加时、结果汇总 |
| 比分权威 | `match_rules.go#MatchScoreState` | 队伍比分、阵营映射、胜负规则判断 |
| 战术记忆 | `match_memory.go` | 跨回合的战术倾向与反制记忆 |

关键设计（`design.md#Decisions 1`）：**比赛层完全不关心回合内部发生了什么**。它只消费回合模拟器返回的自然终局 `RoundTerminal`——哪个队伍赢了、为什么。至于这个胜方是怎么打出来的，是回合引擎的事（第 6 篇起）。

## 2. 常规赛循环：24 回合的骨架

`simulateMatch` 的主循环（`engine.go#simulateMatch`）：

```go
for roundNumber := 1; roundNumber <= e.input.RuleSet.RegulationMaxRounds; roundNumber++ {
    if roundNumber == e.input.RuleSet.RegulationHalfRounds+1 {
        e.swapSides()          // 第 13 回合前换边
    }
    simulation, err := e.roundSimulator.SimulateRound(ctx, e.buildRoundInput(...))
    round, err := e.consumeRoundSimulation(simulation)
    result.Rounds = append(result.Rounds, round)
    if e.state.RegulationComplete(e.input.RuleSet, len(result.Rounds)) {
        break                    // 13 分到点或打满 24 回合
    }
}
```

规则集 `RuleSet` 的字段（`model.go#RuleSet`）：`RegulationHalfRounds=12`（半场回合数）、`RegulationWinRounds=13`（获胜分）、`RegulationMaxRounds=24`（常规赛上限）、加时的 `OvertimeEnabled/HalfRounds/BlockRounds`。这些值来自 `DefaultMR12RuleSet`，由配置常量构造（第 4 篇）——所以"MR12"本身也是配表可调的。

三个细节值得注意：

1. **每回合都检查 `ctx.Err()`**：RPC 可以取消长时间模拟（context 机制），避免一个死循环的回合卡死整个请求。
2. **换边发生在第 13 回合之前**：`RegulationHalfRounds+1 = 13`。CS2 里 T/CT 各有一次半场机会，队伍比分不因换边重置。
3. **早停条件**（`match_rules.go#RegulationComplete`）：任一方到 13 分，或打满 24 回合——后者意味着 12:12 进加时。

## 3. 比分权威性：最容易写错的三个字

换边时，新手直觉会写"交换两队的比分变量"。**这个项目明确拒绝这种做法**，原因在 `design.md#Decisions 1`：

> `MatchState.ScoreByTeam[TeamID]` 是唯一权威比分……SideSwitch 只修改 `SideByTeam`，不得交换或重置队伍比分。`ScoreT/ScoreCT` 仅按当前阵营映射投影。

`MatchScoreState`（`match_rules.go#MatchScoreState`）只有四样东西：两队 ID、`ScoreByTeam`（队伍身份 → 累计分）、`SideByTeam`（队伍身份 → 当前阵营）。`SwitchSides`（`match_rules.go#SwitchSides`）做的事情只有一件：

```go
// 每个队伍的 side 取反，比分一个字都不动
if s.SideByTeam[teamID] == SideT { s.SideByTeam[teamID] = SideCT } else { ... SideT }
```

而对外 DTO 里的 `ScoreT/ScoreCT` 是**投影**出来的兼容字段（`engine.go#consumeRoundSimulation`）：

```go
round.ScoreTeamA = e.state.Score(e.input.TeamA.TeamID)   // 队伍身份，权威
round.ScoreTeamB = e.state.Score(e.input.TeamB.TeamID)
round.ScoreT      = e.state.Score(round.TeamTID)          // 阵营视图，仅兼容
round.ScoreCT     = e.state.Score(round.TeamCTID)
```

为什么要留两个阵营投影字段？**向后兼容旧客户端**：老前端读 `ScoreT/ScoreCT`，新前端按队伍身份算分（第 14 篇会看到 `authoritativeScoreAtPlayback` 的对应处理）。这组字段就是"权威数据 + 兼容投影"并存的典范。

另一个防线：`consumeRoundSimulation` 在加分前**校验终局一致性**（`engine.go#consumeRoundSimulation`）：

```go
expectedSide := e.state.SideByTeam[terminal.WinnerTeamID]
if expectedSide == "" || (terminal.WinnerSide != "" && terminal.WinnerSide != expectedSide) || terminal.WinReason == "" {
    return nil, newError("SIMULATION_INVARIANT_ERROR", ...)
}
```

回合模拟器返回的胜方必须是当前比赛里的队伍、阵营必须与当前映射一致、胜负原因不能为空。三重校验过了，才 `ApplyRoundWinner`（`match_rules.go#ApplyRoundWinner`：`ScoreByTeam[teamID]++`）。**比赛层不信任回合层的任何越权输出**。

## 4. 加时：MR3 双段 block

`playOvertime`（`engine.go#playOvertime`）的结构：

```go
for block := 1; block <= 20; block++ {                    // 最多 20 个 block（防御性上限）
    for inBlock := 1; inBlock <= rule.OvertimeBlockRounds; inBlock++ {  // 每个 block 6 回合
        if inBlock == rule.OvertimeHalfRounds+1 { e.swapSides() }       // 3 回合后换边
        ...模拟一回合...
    }
    if e.state.OvertimeDecided(rule, rule.OvertimeBlockRounds) { return nil }
}
```

CS2 加时是"每 3 回合换边、6 回合一块（MR3）"，**一块打完后分差不为零才结束**。对应代码 `OvertimeDecided`（`match_rules.go#OvertimeDecided`）刻意写成：

```go
func (s *MatchScoreState) OvertimeDecided(rule RuleSet, roundsInBlock int) bool {
    return roundsInBlock >= rule.OvertimeBlockRounds && s.Score(s.TeamAID) != s.Score(s.TeamBID)
}
```

注意它在 block **中间**（比如 3:0）时返回 false——"拒绝在 MR3 block 中间结束比赛"。这是设计文档里的一条硬规则：加时胜负只认"完整 block 结束后的比分差"。

加时回合的 `half` 值继续增长（`2 + block`），前端据此显示 `OT1 · 3/6` 之类的标签（第 14 篇的 `phaseLabel`）。

## 5. 战术记忆：比赛层的"软状态"

除了比分，比赛层还维护 `StrategyMemory`（`match_memory.go`）：每队最近几回合用了什么模板、哪条路线、目标包点、胜败如何。它有两个用途：

1. **喂给下一回合的战术评分**：同战术连胜有加成、连续用同一路线有惩罚、对手被同一打法反复攻击会积累"反制读点"（第 10 篇展开）。
2. **换边时衰减**：`engine.go#swapSides` 先调 `DecayStrategyMemoryForSideSwitch` 再换阵营——攻防角色互换了，阵营相关的记忆要衰减，但队伍风格记忆保留（`doc/simuMatchDesign.md#2.6` 的边界规则）。

记忆的更新在每回合消费后：`consumeRoundSimulation → updateStrategyMemory(round)`。它只影响下一回合的**决策权重**，从不直接改选手属性或战斗公式——这是"战术连续性"与"脚本化"之间的红线。

## 6. 汇总输出：从回合到比赛

`simulateMatch` 收尾做四件事：

1. **比分与胜者**：`FinalScoreTeamA/B` 从权威比分读出；`winnerTeamID()` 比大小（平局返回空串——理论上加时后不会出现，但代码不假设）；
2. **边界事件**：`addMatchBoundaryEvents` 给第一回合补 `match_started`、最后一回合补 `match_ended` 事件（`engine.go#addMatchBoundaryEvents`）；
3. **最终统计**：`buildFinalStats` 聚合每位选手的 K/D/A、ADR（每回合均伤，保留一位小数）、首杀/多杀、下包/拆包数；
4. **可解释报告**：`BuildMatchExplainableReport(result.Rounds)` 汇总全场的 KeyEvents、胜负因素（第 13 篇展开）。

一个防御性细节：`winnerSide`（`engine.go#winnerSide`）返回胜方**当前**阵营——因为加时后双方阵营可能已经又换过边，"胜方当时是 T"和"胜方现在是 T"是两回事，只有队伍身份才是稳定的。

## 本篇回顾

- 比赛层 = 回合循环 + 比分权威 + 战术记忆，完全不关心回合内部。
- 比分只按**队伍身份**累计；换边只换阵营映射；`ScoreT/ScoreCT` 是兼容投影。
- 回合终局进比分前要过三重一致性校验。
- 加时 MR3 双段 block，只在完整 block 结束后允许分胜负。
- 战术记忆只改下一回合的决策权重，不碰属性和战斗公式。
