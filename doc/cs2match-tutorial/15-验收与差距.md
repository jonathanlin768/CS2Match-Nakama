# 15 · 验收与差距：测试、标定与"设计 vs 现实"

> 收官篇。前半部分回答"这套系统怎么证明自己是对的"，后半部分直面"它目前哪里还不达标"——包括那份你一直想看懂的 Review 文档里最硬核的部分：生产断链清单。
>
> 前置依赖：全部。

## 1. 验收的三层金字塔

这个项目对"正确性"的验收分三层，层层递进：

```text
③ 批量标定（10k 场统计分布 vs 目标区间）——调得对不对
② 因果守卫 + 确定性测试——写得对不对
① 单元测试 + 不变量测试——每一步对不对
```

第 ① 层贯穿了前面每一篇（`*_test.go`），这里讲 ② ③。

## 2. 因果守卫：防止"旧病复发"的静态测试

旧引擎的病根是"先抽胜方再补过程"。为了防止它卷土重来，测试目录里有一批**不跑逻辑、扫描源码**的守卫：

| 测试 | 手段 | 守护什么 |
|------|------|---------|
| `causality_guard_test.go#TestCausalSubsystemAPIsRejectPreselectedOutcomeInputs` | AST 静态扫描 | 子系统 API 不接受预选胜方/终局参数 |
| `production_callgraph_test.go#TestProductionCallGraphContainsNoReverseCausalLegacyPath` | 字符串扫描 + import 检查 | 生产代码不含 `resolveRoundWinner` 等旧符号；`matchengine` 不 import `config` 包 |
| `match_orchestration_test.go` | 反射断言 | `MatchInput` 不含 `ForcedRoundWinners/RoundCount/MaxRounds` 字段；`Service` 只有 `Simulate` 一个导出入口 |

这些测试的哲学是：**架构约束也要进 CI**。重写时删掉的"后门"，靠测试保证永远关着。

## 3. 确定性测试：同 seed 必须逐事件一致

`round_engine_test.go#TestCausalRoundEngineSameSeedDeepEqual` 与 `engine_test.go#TestProductionMatchDeepEqualAcrossMapInsertionOrder` 回答两个问题：

1. 同一 `MatchInput + seed` 跑两遍 → 结果 **deep equal**（第 1 篇的确定性原则）；
2. **map 插入顺序不同** → 结果不变（第 8 篇"map 无序靠排序"原则的验收）。

第 2 条尤其重要：Go 的 map 遍历顺序随机，如果任何一条路径漏了排序，测试就会在某个插入顺序下翻车。这两条测试是整个确定性设计的"总闸"。

## 4. 批量标定：10k 场的统计验收

`calibration.go#CalibrateRounds` 用 worker 池并行跑批量回合（样本数 = CPU 核数对齐，每样本独立派生 seed），`aggregateCalibration` 汇总指标。两个防偏设计：

- **交替阵营**（`calibrationInput`）：`index%2==1` 时交换 TeamT/TeamCT——把"队伍强度"和"阵营优势"拆开，避免强队恰好总打 T 造成假象；
- **只调配置不调公式**：标定结论只允许改 Luban 表（`calibration-summary.md` 的立场），禁止加目标胜方、重采样或测试钩子（`design.md#Decisions 20`）。

`SIMU_LONG_CALIBRATION=1` 跑 10k 场后的实测 vs 目标（`calibration-summary.md`）：

| 指标 | 目标 | 实测 | 结论 |
|------|------|------|------|
| T 胜率 | 45–55% | 51.09% | ✅ |
| 平均击杀 | 6.5–8.5 | 5.46 | ❌ 偏低（击杀密度不足） |
| 下包率 | 30–45% | 51.27% | ❌ 偏高 |
| 拆包率 | 8–18% | 12.56% | ✅ |
| 爆炸率 | 15–30% | 14.48% | ⚠️ 差 0.52pp |
| 首杀方胜率 | 60–75% | 61.56% | ✅ |
| 5v3 胜率 | 80–92% | 72.87% | ❌ 人数优势滚雪球不足 |
| 3v5 翻盘率 | 3–10% | 27.13% | ❌ 偏高 |
| 平均回合时长 | 45–85s | 59.73s | ✅ |

终局分布：`bomb_secured` 3035 / `timeout` 3792 是大头，`bomb_defused` 只有 644。**这些偏差被如实保留在文档里，没有为了好看而改口径**——"标定不是验收因果正确性的替代品"（`design.md#Decisions 20`）。偏差指向的方向也一致：击杀太稀、下包太易、5v3 打不出碾压——大概率与第 6 节的情报/拦截断链相关（信息太少 → 决策保守 → 对枪少、转点少）。

## 5. OpenSpec：这个项目的工作流

本专栏一直在引用的提案，就是 OpenSpec 工作流的产物。`openspec/changes/implement-causal-simu-match-engine/` 目录里每个文件的职责：

| 文件 | 职责 |
|------|------|
| `proposal.md` | 为什么改、改什么（Why / What Changes） |
| `design.md` | 22 个工程化 Decisions + Risks + Migration + Open Questions |
| `tasks.md` | 任务清单（实现时逐条勾选） |
| `specs/*/spec.md` | 三个 capability 的 delta 规格（ADDED/MODIFIED/REMOVED 的 SHALL 要求） |
| `traceability.md` | 设计 → 规格 → 任务 → 实现 → 测试的追踪表 |
| `verification-summary.md` / `calibration-summary.md` / `config-inventory.md` | 验收声明 / 标定结果 / 配置稳定 ID 清单 |

工作流四步：**propose**（生成 proposal/design/tasks/specs）→ **apply**（按 tasks 实现）→ **sync**（delta 规格并入 `openspec/specs/` 主规格）→ **archive**（change 移入 `archive/`）。本项目的旧 MVP change 就归档在 `archive/2026-08-01-complete-simu-match-mr12/`。

对你未来的意义：**想给引擎加新功能（比如武器表、经济系统、第二张地图），先走 propose**，让规格先于代码。这也是 `AGENTS.md` 里"任何指令都先查 OpenSpec"的原因。

## 6. 设计 vs 现实：生产断链清单

这是你最初想要的 Review 的核心结论。按"影响正确性"和"影响维护"分两档（来源：`doc/reviews/ebc8906-review-guide.md#12/13`，本专栏写作时已逐条用 grep 复核过生产调用点）：

### 6.1 影响行为/正确性（高优先）

| # | 断链 | 事实 |
|---|------|------|
| Q1 | **同秒跨行动批次原子性未实现** | `round_engine.go#resolveTimestamp` 逐行动顺序结算；脉冲内原子（✅ 第 12 篇），跨行动无批次快照。同秒的第二个行动能看到第一个的结果。 |
| Q2 | **TeamIntel 生产未接线** | `intel.go#RecordIntel/DegradeIntelForObserverDeath/IntelScoreModifier` 零生产调用，`view.Intel` 恒空。AI 目前只有 KnownControl，"声音/死亡/空点情报"全缺——与下包率偏高、5v3 不足的标定偏差高度相关。 |
| Q3 | **移动拦截与边上进度生产未生效** | `movement.go#ScheduleInterceptCheck/InterruptMovementForEncounter/UpdateMovementProgress` 零生产调用；移动中位置停在 `Progress=0`，接触靠 `discoverEncounters` 同节点/可见判定。 |
| Q4 | **NoProgress 恢复的"成功"分类生产不可达** | `noop.go#CompleteNoProgressRecovery` 仅测试调用；生产里 `NoProgressEligible` 只能走"恢复行动调度失败"分支（第 13 篇）。 |

### 6.2 影响维护/与设计文档有出入（中低优先）

| # | 事项 | 事实 |
|---|------|------|
| Q5 | 开局重试与默认模板兜底未接生产 | `opening_plan.go#planOpening`（attempt 0/1 + Default 模板回退）仅测试调用，生产只跑 attempt 0。 |
| Q6 | `PlanSiteContest` 被绕过 | 生产用"自动下包门槛"替代站点争夺决策。 |
| Q7 | **隐藏平衡常量** | `combat.go#defaultCombatModifiers`（`(Damage−30)/2 + RPM/600`、`/10`、`8`、`6/3/−5/2`）、`CalculateCoordination`（`(n−1)×2` 等）、`CalculatePlantScore/DefuseScore`、`decision.go` 的字面量写死在代码里，与"全部参数进配表"的规格有张力。 |
| Q8 | 主规格残留旧 MVP 要求 | `openspec/specs/simu-engine-core/spec.md` 仍含已 REMOVED 的旧要求，与 delta 冲突。 |
| Q10 | Hold 语义 | `StartHoldAction` 的 `ActionHoldStart` 立即完成、每循环重建（与设计文档"持续 Intent"措辞不同，功能等价）。 |
| Q11 | 死代码 | `ActionRoundExpire/IntelDecay/ControlDecay` 从不被调度（由 `NextTime` 直接处理，功能等价）。 |
| Q13 | 追踪表引用失真 | `traceability.md` 引用了不存在的文件名（如 `phase.go`、`planner.go`）。 |

### 6.3 怎么读这张清单

三点提示：

1. **"断链"≠"写错了"**——被断开的代码单元测试全绿（第 9 篇的拦截管线就是例子）。它们是"按设计实现了、但没接进生产循环"的**准死代码**。
2. **Q2/Q3 是最高杠杆的修复目标**：情报与拦截一旦接线，AI 的信息边界立刻真实化，标定里的"下包率 51%、5v3 只有 73%"偏差很可能同步改善。
3. **先读规格再动手**：任何修复前先对照 `openspec/specs/simu-*-*` 与 `design.md` 的对应 Decision——这些断链本身可能就是下一次 OpenSpec change 的提案素材。

## 7. 结语：你现在的工具箱

15 篇走完，你应该已经拥有：

- **一条完整链路**：Excel 数字 → 校验快照 → 战术选择 → 离散事件回合 → 脉冲伤害 → 终局 → 战报 → 回放页；
- **一张依赖地图**：52 个后端文件 + 前端回放链路的职责与调用关系；
- **一份缺口清单**：哪里"测试绿但生产断"，哪里藏着手写的平衡常量；
- **一套方法**：OpenSpec 提案驱动 + 确定性测试 + 因果守卫 + 批量标定。

最后一句提醒：这套引擎的文档、规格、Review 与代码**可能互相不一致**（Q8、Q13 就是例子）。读任何一份资料时，都回到那条铁律——**行为以当前代码为准，意图以设计文档为准，验收以主规格为准**，三者打架的地方，就是下一个提案的起点。
