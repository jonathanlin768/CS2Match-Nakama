# 10 · 战术选择与 AI 决策

> 这篇讲引擎的"大脑"：开局怎么选战术、CT 为什么不能偷看 T 的底牌、中期决策读到的世界长什么样。以及一条贯穿全篇的红线——**信息边界**。
>
> 前置依赖：07（权威状态）、08（行动与调度器）。

## 1. 开局三步：选模板 → 造计划 → 部署

回合第一帧（`round_engine.go#runCausalRound` 开头）的三连击：

```go
tSelection  := SelectStrategyTemplate(...)   // T 从 6 个战术模板里选一个
ctSelection := SelectCTSetup(...)           // CT 从 3 个 setup 模板里选一个
plan        := BuildRoundPlan(input, tSelection.Template, ctSelection.Template)
state       := NewRoundState(input, plan)
DeployOpeningActions(state)                 // 生成开局 Move/Hold 行动
```

`BuildRoundPlan`（`strategy.go#BuildRoundPlan`）负责三件事：

1. **角色分配** `AssignRoles`（`strategy.go#AssignRoles`）：按模板的 `RequiredRoles` 贪心匹配。`roleFitScore` = 对应属性分 + 选手带该角色标签则 +100；匹配不上就用"最接近者"顶上，但要吃 `ROLE_GAP` 的 −5 惩罚（比如让没标签的人打 Entry）。没分到核心角色的人拿 `Rifler` 或自己的第一个标签。
2. **路线分配** `assignOpeningRoutes`：按模板的 `RouteAllocations`（路线 → 人数）把选手塞进路线，人数必须与路线 min/max 匹配、必须恰好分配完 5 人——校验失败直接 `INVALID_OPENING_PLAN`。
3. **选持包人** `SelectBombCarrier`（`strategy.go#SelectBombCarrier`）：基础分 = (Composure + Discipline)/2；Entry 减 40（突破手不背锅）、Support 加 10；还要求该选手的路线从 T_SPAWN 可达（不可达的持包人没有意义）。

`DeployOpeningActions`（`strategy.go#DeployOpeningActions`）把计划变成行动：每个选手沿自己的路线走到下一个节点（用模板的 `Tempo` 决定移动节奏），已经在位的防守方生成 `HoldStart` 架点行动。**开局部署不消耗回合时间**——等价于 freeze time（`doc/simuMatchDesign.md#3.3`）。

## 2. 战术评分：七个修正项，一个公式

`ScoreStrategyCandidates`（`strategy.go#ScoreStrategyCandidates`）给本阵营每个模板打分：

```text
DeterministicScore =
    TemplateBaseWeight（模板场景平均基础权重）
  + LineupFitScore（阵容关键属性匹配度 ×0.4）
  + ScorePressure（落后追赶分，clamp ±6）
  + PreviousSuccessBonus（近期同模板胜利加成，有上限）
  − RepeatPenalty（连续用同模板的惩罚）
  − CounterReadRisk（对手被同打法打多了的"反制读点"）

FinalScore = clamp(DeterministicScore + RandomNoise, MinStrategyWeight, MaxStrategyWeight)
```

逐项说人话：

- **ScorePressure**（`strategy.go#scorePressure`）：落后方更愿意赌——分差 ×0.25，落后且模板是快节奏（fast）时系数翻倍到 0.5。领先方则天然偏向稳妥模板。
- **PreviousSuccessBonus**：最近 `StrategyRepeatWindow` 内同模板赢过，加成 = 胜场 × `SuccessBonusPerRound`，封顶 `MaxPreviousSuccessBonus`。
- **RepeatPenalty**：`StrategyRepeatWindow` 内同模板使用次数超过 `RepeatFreeCount` 后，每多一次扣 `StrategyRepeatPenalty`。
- **CounterReadRisk**：`CounterReads[模板]`（对手最近被这打法打过的次数）× `CounterMemoryBonus`。

这正是设计文档里"连续 5 局 Rush B"例子的落地（`doc/simuMatchDesign.md#2.6`）：没有"第 6 局强制换战术"的硬规则，但惩罚项会自然让评分翻盘——高 Discipline/Awareness 的队伍更早调整，头铁队继续 Rush B，都是评分的自然结果。

**噪声与"明显优势保护"**：`RandomNoise` 幅度由 `strategyNoiseAmplitude`（`strategy.go#strategyNoiseAmplitude`）决定——队伍平均 Discipline、Awareness 和 IGL 的 Gamesense 越高，稳定性越高、噪声越小。`protectDecisiveStrategyTrend`（`strategy.go#protectDecisiveStrategyTrend`）保证：若确定性分差达到 `DecisiveScoreGap`，噪声被钳制在"不足以翻转名次"的范围内。**噪声可以影响选择，但不能让明显的优劣关系翻盘**——与战斗层的 `protectEncounterTrend` 是同一哲学（第 11 篇）。

排序规则：FinalScore 降序，同分按 TemplateID 字典序。`SelectStrategyTemplate` 取第一名。

> **阅读提示（随机数的两套入口）**：策略评分直接用 `stableUnit`（种子派生的 [0,1) 值，`movement.go#stableUnit`），中期决策则走 `RollSource` 接口（生产用 `IdentityRollSource` 包装同一个派生种子）。两套入口行为一致、只是历史演进的并存——读代码时别被"两种取随机数的写法"迷惑。

## 3. CT 独立性：底牌不可偷看

`SelectCTSetup`（`strategy.go#SelectCTSetup`）是整个信息边界设计的代表作：

```go
// SelectCTSetup intentionally has no T plan/template argument. Its seed and
// inputs are restricted to CT-owned state and match memory.
func SelectCTSetup(config *MapConfig, ctTeam TeamInput, scoreFor, scoreAgainst int,
    memory StrategyMemory, roundSeed int64, attemptOrdinal int) (StrategySelection, error) {
    ctSeed := deriveSeed(roundSeed, "ct_setup", attemptOrdinal)
    return SelectStrategyTemplate(config, ctTeam, SideCT, ...)
}
```

两个事实：

1. **签名里没有 T 模板参数**——CT 在选防守阵型时根本不知道 T 这把要打 A 还是 B；
2. **种子也是隔离的**——`ctSeed = deriveSeed(roundSeed, "ct_setup", attemptOrdinal)`，即使内部实现未来想偷看，随机流也与 T 的分开了。

那 CT 靠什么选？自己的阵容、自己的比分压力、自己的战术记忆，以及模板的 `Side=CT` 过滤。T 模板里的 `common_ct_setup_ids` 只是赛前先验（"Dust2 上 CT 常见站位"），**不得**决定本回合 CT 的实际选择——配置校验里专门检查只有 T 模板能引用它（第 4 篇）。

> ⚠️ **设计 vs 现实提示**：`opening_plan.go#planOpening`（含 attempt 0/1 重试与 `DefaultStrategyTemplateID`/`DefaultCTSetupTemplateID` 兜底）在生产代码中无调用者。生产的 `runCausalRound` 只做一次 attempt 0，失败直接返回 `INVALID_OPENING_PLAN`——"重试与兜底"路径目前只活在测试里（Review 指南 Q5）。

## 4. 中期决策：指纹差分触发

开局之后，AI 还要在回合中不断"重新决策"（转点、补防、强攻、保枪）。触发机制是**指纹差分**（`decision.go#DetectDecisionTriggers`）：每轮循环前拍一张 `DecisionFingerprint`（人数、资源带、认知控制权、炸弹状态、活跃遭遇战数……），批次结算后再拍一张，**对比差异**：

| 触发类型 | 差分信号 |
|---------|---------|
| `EncounterEnd` | 活跃遭遇战数量减少（打完一场） |
| `ResourceBandChanged` | 有人从"健康"掉进"低资源带"（HP/Focus/Stamina 最小值 <30/60 两档） |
| `ControlChanged` | 认知控制权变化（我方视野里的点易主） |
| `EmptySite` | 空点情报集合变化（当前生产恒空，见下） |
| `BombChanged` | 炸弹状态或位置变化（掉包/下包） |
| `ForceExecuteThreshold` | Timeline 跨过 `RoundDeadline − 60s` 的强攻预警线 |

另外还有 `PostPlantArrival`、`DefuseInterrupted` 等显式触发。有触发 → `scheduleDecisions`（`round_engine.go#scheduleDecisions`）为双方各生成一个决策行动。

## 5. 决策的"世界"：DecisionView 与候选评分

决策前先构造视图 `BuildDecisionView`。关键不在于它有什么，而在于它**没有什么**（`design.md#Decisions 10`）：

```text
DecisionView 包含：本方选手的公开状态、位置、行动状态；
                  本方 KnownControl（认知控制权）；
                  本方 TeamIntel（情报，当前恒空——已知缺口）；
                  炸弹的"已知"信息（下包后知道点位，下包前不知道精确位置）；
                  比分、时间、阶段。

DecisionView 不含：敌方 Intent、敌方 ActionQueue、敌方 ActualControl、
                  未被观察到的炸弹精确位置、敌方隐藏计划。
```

候选打分 `ScoreDecisionCandidates` 分阵营：T 有 `Continue/Rotate/ForceExecute/RecoverBomb/Plant/GatherIntel/HoldFlank`，CT 有 `InterceptRotate/Reinforce/Hold/Retake/Defuse/Save/DenyDefuse`（`decision.go` 的 14 个 `DecisionType`）。评分要素包括路线价值（短路线分高、加上沿途控制权修正）、选手资源执行分（`resourceExecutionScore` = (HP+Focus+Stamina)/6）、情报缺口分等。同样有 `protectDecisionTrend` 保护明显优势不被噪声翻转，噪声幅度同样受 IGL/Discipline/Awareness 约束（`decisionNoiseAmplitude`）。

**低置信度信息只影响评分，不触发确定性动作**——这是设计文档的情报原则（`doc/simuMatchDesign.md#2.6`）：30% 置信度的"B 点可能有人"只让补防 B 的分数高一点，而不是无脑拉人过去。

## 6. 决策落地：结果必须是真实行动

`ScheduleDecision`（`decision.go#ScheduleDecision`）安排一个 `DecisionResolve` 行动（延后 `DecisionDelay` 秒），同时过三道闸：

1. `DecisionCount >= MaxDecisionCount`（3）→ 只放行"可强制执行"类（如强攻、残局救包），普通决策拒绝；
2. 候选是转点类且该队转点次数已达 `MaxRotationsPerTeam`（3）→ 同上；
3. 通过则 `DecisionCount++` / `RotationCount[side]++`。

`ResolveDecision`（`decision.go#ResolveDecision`）到点时把候选**翻译成真实行动**：`Plant → StartPlantAction`、`Defuse → StartDefuseAction`、`RecoverBomb → ScheduleBombRecovery`、`Hold/Save → StartHoldAction`、其余 → `startDecisionMove`（寻路 + 移动）。**决策不直接改状态**——它只产出行动，行动走调度器、resolver 的正常链路。`forceReachableCandidate` 是最后防线：强制类决策如果目标不可达，就替换成"最近可达包点/炸弹"的可行版本，找不到才放弃。

一个实现细节：`StartHoldAction`（`decision.go#StartHoldAction`）生成的 `ActionHoldStart` 是 `ResolveAt == StartAt` 的即时行动——"架点"在引擎里不是持续过程，而是一个每轮循环可重建的占位状态（这是 Review 指南 Q10 指出的与设计文档措辞的差异，功能上无害但值得知道）。

## 7. 情报模型：完整但未接线的地基

`intel.go` 里的情报系统设计完整：`IntelRecord` 带 `Type/Source/Confidence/ExpiresAt`，置信度分五层（90–100 直接视野、71–89 交火确认、30–70 声音与死亡信息、1–29 空点假设、0 不可用），`RecordIntel` 写入、`DegradeIntelForObserverDeath` 观察者死亡降级、`DecayIntelAndControl` 批量过期。

**但生产路径从不调用 `RecordIntel`**——`view.Intel` 恒为空（Review 指南 Q2）。当前 AI 实际依赖的信息源是：公开状态 + `KnownControl`（由 `ResolveContest` 在遭遇战结算时写入）。这意味着"声音线索""死亡情报""空点假设"目前是设计到位、接线缺席的状态，第 15 篇会把这条断链的前因后果讲透。

## 本篇回顾

- 开局三连：T/CT 独立选模板 → 角色/路线/持包人 → 部署 Move/Hold。
- 战术评分七项修正，噪声受 IGL/Discipline/Awareness 约束，明显优势不被噪声翻转。
- CT setup 的签名与种子都不含 T 计划——信息边界的代表作。
- 中期决策靠指纹差分触发；DecisionView 不含敌方隐藏状态。
- 决策只产出真实行动；三道闸限制决策与转点次数。
- TeamIntel 设计完整但生产未接线，AI 目前靠 KnownControl。
