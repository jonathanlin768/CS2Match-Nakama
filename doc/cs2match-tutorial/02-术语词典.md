# 02 · 背景知识与术语词典

> 这篇是专栏的"武器库"。前半部分补三个你不太熟的技术栈的最小背景（Nakama、Go、Luban），后半部分是引擎专有名词词典。**第一遍全讲，之后正文不再重复解释**，遇到忘了的回到这里查。

## 1. Nakama：服务端长什么样

Nakama 是一个开源游戏服务器（本项目用 3.30.0），负责账号、好友、聊天、存储和**自定义逻辑**。它跟本引擎相关的只有两个概念：

### 1.1 Go 插件（plugin）

Nakama 本体是二进制，业务逻辑以 **Go 插件**形式编译成 `.so` 动态库，Nakama 启动时加载它。本项目的插件入口在 `server/` 目录（module 路径 `windypath.com/cs2match/server`），编译产物注入 Docker 里的 Nakama 容器。

插件里注册的钩子之一就是 RPC。

### 1.2 RPC（Remote Procedure Call）

客户端调一个命名函数、传 JSON、拿 JSON 返回，类似 HTTP 接口但走 Nakama 的会话协议。本引擎的正式入口就是一个 RPC：

```text
客户端 → DebugSimuMatch RPC { map_id, seed } → 服务端算完整场比赛 → MatchResult JSON
```

注册位置在 `server/internal/match/api_rpc.go`（函数 `RegisterRPC`，路由名 `DebugSimuMatch`，细节见第 3 篇）。**没有实时连接、没有逐帧下发**——一次请求，一场完整比赛。

> 为什么叫 Debug 却是正式入口？历史原因：早期它就是调试接口；重写后提案规定"不新增 RPC，继续用它"，但它内部走的完全是正式模拟路径（`openspec/changes/implement-causal-simu-match-engine/proposal.md#Impact`）。

## 2. Go 语言：你会反复遇到的特性

不需要系统性学 Go，只需认识这几样（教程中遇到会再指回这里）：

| 特性 | 一句话 | 在引擎里的典型位置 |
|------|--------|-------------------|
| `struct` | 字段集合，类似 TS 的 interface 但带内存布局 | `RoundState`、`ScheduledAction` |
| `map[string]X` | 键值表；**遍历顺序随机**，所以确定性代码必须显式排序 | `state.Players`（遍历前总 `sort.Strings`） |
| `slice []X` | 动态数组 | `action.ActorIDs` |
| 方法接收者 `func (s *T) M()` | 挂在类型上的函数；`*T` 表示可以改原对象 | `state.AdvanceTimeline` |
| `interface{}` | 任意类型，类似 `any` | `ActionPayload` 的宽接口、事件 `Extra` 字段 |
| `error` 返回值 | 不抛异常，函数返回 `(结果, error)` | 几乎所有引擎函数 |
| `container/heap` | 标准库优先队列 | `scheduledActionHeap` |

两条 Go 惯例值得现在就记住：

1. **"错误是值"**：引擎不 panic，失败一律返回带稳定错误码的 `*EngineError`（如 `INVALID_MATCH_INPUT`、`SCHEDULER_LIMIT_EXCEEDED`）。RPC 层把错误码原样带给客户端。
2. **"map 无序"**：所有进入 ID、排序、战报的遍历，代码都会先收集 key 并 `sort.Strings`。这是确定性原则在语言层面的代价。

## 3. Luban：策划配表工具

Luban 4.5.0 是项目的配表管线：策划在 Excel（`configs/Datas/*.xlsx`）里维护数据，Luban 导出生成 **Go 结构定义 + JSON 数据**，服务端和客户端各拿一份 JSON 副本。

```text
configs/Datas/#RouteTemplate.xlsx（策划源表，Source of Truth）
        │ Luban 导出
        ├── server/config/*.go            （生成的表结构代码）
        ├── server/config/data/*.json     （服务端运行时数据）
        └── client/public/data/config/*.json（客户端副本，字节级一致）
```

引擎本身**不直接读这些表**——业务层把它转成自包含的 `MapConfig` 快照再交给引擎（第 4 篇详解）。

## 4. 引擎专有名词词典

按"从大到小"排列。每个词给出：**含义 → 出现位置 → 深入篇目**。

### 4.1 宏观概念

| 名词 | 含义 | 深入 |
|------|------|------|
| **Causal Simulation（因果模拟）** | 先结算状态变化（移动/伤害/炸弹），最后才判定胜负；胜方不能反过来决定事件 | 01、06 |
| **Discrete Event Scheduler（离散事件调度器）** | 不逐秒循环；每个行动冻结绝对时间 `ResolveAt`，引擎跳到最早到期事件结算 | 06、08 |
| **语义地图（Semantic Map）** | 由 `MapNode/MapEdge/Route/Visibility` 组成的战术语义图，**不是物理导航网格** | 09 |
| **Authoritative State（权威状态）** | 引擎内部唯一真值（`RoundState`）；对外 DTO 只能从它投影，不能反向写回 | 07 |
| **Deterministic Seed（确定性种子）** | 以 `MatchInput.Seed` 为根，派生每回合、每行动、每次采样独立种子；不共享可变随机流 | 04、12 |

### 4.2 回合与行动

| 名词 | 含义 | 深入 |
|------|------|------|
| **Intent / ActionInstance / BusyInterval** | 行动三层模型：战术意图（持续）→ 一次执行（可打断）→ 时间占用（互斥） | 08 |
| **ActionVersion（行动版本）** | 每个选手的递增版本号；行动构造时冻结版本，结算时版本不匹配即失效（防"幽灵完成"） | 08 |
| **同秒优先级（Same-Second Priority）** | 同一 `ResolveAt` 的行动按固定优先级结算：战斗伤害(100) > 后效(90) > 掉包(80) > 下包完成(70) > 拆包完成(60) > 爆炸(50)… | 08、13 |
| **CombatPulse（战斗脉冲）** | 一次遭遇战内的一个"射击窗口"；同一脉冲的全部伤害基于同一快照采样后**原子应用** | 12 |
| **Effect / AppliedBatch** | 结算产物：resolver 只产出 Effect，由应用层统一落地并投影事件 | 08、12 |

### 4.3 状态与信息

| 名词 | 含义 | 深入 |
|------|------|------|
| **RoundState** | 单回合权威状态容器：Timeline、玩家、炸弹、节点控制权、情报、调度器、终局 | 07 |
| **BombState** | 炸弹独立实体的权威状态：`Carried/Dropped/Planting/Planted/Defusing/Defused/Exploded` | 07、13 |
| **ActualControl vs KnownControl** | 引擎真实控制权 vs 每方"认知"的控制权；AI 只能读本方 KnownControl | 07、10 |
| **TeamIntel（队内情报）** | 每方独立的情报记录（视野/交火/声音/死亡/空点/炸弹），带 confidence 与 TTL | 10 |
| **Node XOR Edge** | 位置不变量：选手要么在节点上，要么在一条边上，二者必居其一且只居其一 | 07、09 |
| **OnEdgeLocation（边上位置）** | 移动中被拦截时的运行时位置：边 ID、进度 `Progress`、坐标、显示名 | 09 |

### 4.4 战斗与规则

| 名词 | 含义 | 深入 |
|------|------|------|
| **Encounter（遭遇战）** | 一次有明确参战人员的局部战斗；只调度未来脉冲，**不预生成伤亡表** | 11 |
| **PlayerCombatScore** | 唯一冻结的个人战斗分公式（九项）；攻击方在脉冲里只使用这一套分 | 11 |
| **EncounterScore** | 团队级结算分（个人分 + 团队修正 + 随机噪声）；只决定主动权/脉冲数/撤退倾向，**不直接定胜者** | 11 |
| **HitChance / KillChance** | sigmoid 命中率；`KillChance = min(HitChance × DamagePotential × Exposure, HitChance)`，恒 ≤ 命中率 | 11、12 |
| **MR12 与加时** | 每队 12 回合半场、13 分胜；加时 MR3 双段 block，比分按队伍身份累计，换边只换阵营 | 05 |
| **NoProgress（无进展兜底）** | 连续无进展达阈值 → 一次确定性恢复尝试 → 仍失败才产生 `no_progress_timeout` 终局 | 06、13 |

### 4.5 输出与解释

| 名词 | 含义 | 深入 |
|------|------|------|
| **EventReason（事件原因）** | 每个事件的可审计原因：主因、公式、输入、结构化修正、公开状态变化 | 13 |
| **ExplainableReport（可解释战报）** | 从实际 ReasonRecord 聚合的 KeyEvents、StrategySummary、LossReasons、WinFactors | 13 |
| **RoundTerminal（回合终局）** | 纯函数 `EvaluateRoundTerminal` 从批次后状态推导的 `Winner/WinReason` | 13 |
| **投影（Projection）** | 把内部权威状态转换成对外 DTO 的过程；只读，永不写回 | 07、13 |

## 5. 代码目录地图

先记住两张地图，读代码时不会迷路：

```text
server/internal/framework/matchengine/   ← 引擎本体（不依赖 config 包）
  engine.go          整场编排：MR12/换边/加时/结果汇总
  match_rules.go     权威比分与换边（MatchScoreState）
  match_memory.go    跨回合战术记忆（StrategyMemory）
  round_engine.go    单回合离散事件主循环（runCausalRound）
  round_state.go     权威回合状态与不变量
  action.go          Intent/Action/Effect/ID 派生
  scheduler.go       确定性优先队列与 deadline 选择
  movement.go        语义移动与拦截
  strategy.go        战术模板评分与选择
  opening_plan.go    开局计划与角色分配
  decision.go        中期决策
  intel.go           情报与认知控制权
  encounter.go       遭遇战生命周期
  combat.go          评分、脉冲、命中与伤害
  effect_apply.go    Effect 原子应用与死亡派生
  utility.go         道具预算
  bomb.go            炸弹状态机
  terminal.go        纯终局判定
  noop.go            无进展检测与恢复周期
  event_projection.go / round_projection.go  战报投影
  validation.go      配置校验与错误码矩阵
  calibration.go     批量标定
  model.go           对外输入/输出模型
  seed.go            种子派生
  *_test.go          单测（也是重要学习材料）

server/internal/match/                    ← 业务适配层（Nakama RPC）
  api_rpc.go         RPC 注册与解码
  service.go         构造 MatchInput 并调用引擎
  config_adapter.go  Luban 表 → MapConfig 快照

client/src/pages/BattlePage.tsx           ← 前端回放入口
client/src/pages/battle-playback.ts       ← 回放纯函数
client/src/types/match-report.ts          ← DTO 类型
client/src/components/battle/*            ← 回放 UI 组件
```

**一张心智图记住依赖方向**：

```text
match(RPC 适配) ──构造输入──▶ matchengine(引擎) ──只消费──▶ MapConfig 快照
client(回放) ──只读──▶ MatchResult JSON（引擎输出）
引擎不 import config 包；前端不参与任何结算。
```

## 本篇回顾

- Nakama = 插件 + RPC：一次请求，一场完整比赛，无实时同步。
- Go 两条命脉：错误是值（不 panic）；map 无序（确定性靠显式排序）。
- Luban = 策划 Excel 是 Source of Truth，导出 JSON 供两端消费；引擎只认 `MapConfig` 快照。
- 词典里加粗的名词，是后面每一篇的地基，忘了就回来查。
