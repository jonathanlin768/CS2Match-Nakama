# 09 · 语义地图与移动

> 这篇讲"空间"：引擎里的 Dust2 不是 3D 模型，而是一张**战术语义图**。选手怎么在这张图上移动、移动中怎么表达位置、以及"走到一半被截住"这件事在引擎里意味着什么。
>
> 前置依赖：04（配置）、07（权威状态）。

## 1. 语义地图：四张表拼出的 Dust2

引擎的空间模型由四类配置组成（`doc/simuMatchDesign.md#2.1`），全部进入 `MapConfig` 快照：

| 结构 | 是什么 | 关键字段 |
|------|--------|---------|
| `MapNode`（20 个） | 语义节点：出生点、通道、包点、架点 | `x/y`（雷达归一化坐标 0–1）、`site`、`node_type`、`area_usages`、`shape`（None/Circle/Polygon） |
| `MapEdge`（19 条） | 节点之间的路径 | `base_time`（基础耗时）、`stamina_cost`、`risk`、`noise`、`risk_points`、`intercept_nodes`、`bidirectional` |
| `Route`（16 条） | 有序节点序列（战术路线） | `nodes`、`min/max_players`、`style_tags` |
| `Visibility`（12 条） | 点位间可见关系 | `visible`、`range`、`angle_advantage`、`cover/exposure_modifier` |

**这张图不做物理仿真**：没有碰撞体、没有弹道、没有连续寻路。设计文档给它定了性（`doc/simuMatchDesign.md#1.1`）：

> 地图、视野、转点与炸弹不是事后叙事标签：它们分别由语义 MapNode/MapEdge/Route、可见性与情报、可打断 ScheduledAction 以及权威 BombState 参与实际结算。

也就是说，`T_SPAWN → LONG_DOOR → A_LONG` 这条路线上的每一步耗时、每一步的暴露风险，都真实参与了行动调度——只是空间被抽象成了"图"。

`MapNode` 的 `area_usages` 里还有三个值得记住的语义标记：`Plant`（可下包点，校验 A/B 包点存在就看它）、`KillSample`（击杀事件优先在此节点区域内采样坐标）、`Risk`（赛前配置的风险热点，影响拦截概率与事件位置采样权重）。`shape=Circle/Polygon` 则给战报坐标提供了采样区域（第 13 篇的事件位置）。

## 2. 移动的本质：一段有代价的边

一次移动（`movement.go#StartMovement`）做的事情：

1. 校验：全员存活、同一起点、目标边可达（`bidirectional` 边可反向走）；
2. 计算耗时 `ResolveMoveDuration`（`movement.go#ResolveMoveDuration`）：

```text
duration = BaseTime × tempoFactor + FormationPenalty + staminaPenalty − mobilityModifier
clamp 到 [MinMoveTime, MaxMoveTime]

tempoFactor：fast/rush → 0.85，slow → 1.15，默认 1
staminaPenalty = max(0, MaxStamina − 全组平均Stamina) / 20
mobilityModifier = (全组平均Mobility − 50) / 20
```

看到没——**CS2 的一切都被压缩成了数值**：快攻走得更快（但更耗体能、更暴露，见 `MoveProfile`），体能低的队伍跑得慢，Mobility 高的选手省时间。这是"少模拟，多结算"的典型例子：不模拟跑步动作，只结算"这段路要花多久"。

3. 构造 `ActionMovementArrive`（优先级 20、`MinRequiredActors` = 组人数），`BeginExclusiveAction` 锁定选手（第 8 篇）；
4. **立刻把选手位置落到边上**：`ResolveOnEdgeLocation(progress=0)`——选手进入 `Node XOR Edge` 的"Edge"态；
5. 持包者同步 `Bomb.Location`，行动入队。

## 3. 边上位置：OnEdgeLocation

移动中被打断时，选手"在哪"必须有答案。答案就是 `OnEdgeLocation`（`action.go#OnEdgeLocation`）：

```go
type OnEdgeLocation struct {
    EdgeID      string
    FromNode    string
    ToNode      string
    Progress    float64   // 0..1，在边上的进度
    X           float64
    Y           float64
    DisplayName string    // "A大门 → A大" 这类战报用名
}
```

配套的 `UpdateMovementProgress`（`movement.go#UpdateMovementProgress`）按时间比例重算进度和坐标：

```text
progress = (now − StartAt) / (ResolveAt − StartAt)
坐标在两端点之间插值，并加 ±0.008 的正弦抖动
（抖动种子 = stableSignedUnit(seed, "edge_x"/"edge_y", edge.ID, 选手身份)）
```

注意那个抖动：它**不是随机游走**，而是由种子派生的确定性函数——同一场比赛重跑，同一个选手在同一时刻站在完全相同的像素上。确定性原则连"走路时的微小晃动"都不放过。

被打断后恢复移动走 `ResumeInterruptedMovement`（`movement.go#ResumeInterruptedMovement`）：从当前 `Progress` 按比例续走，**已消耗的时间不退还**——中断是有代价的，这符合直觉。

> ⚠️ **设计 vs 现实提示**：`UpdateMovementProgress` 在生产代码中没有调用者——生产中的移动是"起点瞬间、到达瞬间"，中间停留 `Progress=0` 的起点坐标（遭遇战接触触发靠的是 `discoverEncounters` 的"同节点或可见"判定，不依赖边上进度）。这是 Review 指南的 Q3，第 15 篇汇总。

## 4. 寻路：有界的确定性路径选择

引擎不做 A* 全图寻路，只做**配置语义图上的有界 Dijkstra**（`movement.go#FindBoundedPath`）：

- 图 = 节点 + 边（双向边两条方向）；
- 展开上限 `maxExpansions`（调用方默认传 `len(Nodes)×4`）——**有界**，防止病态图拖死引擎；
- 距离相等时按边的字典序决胜——**确定性**；
- 无路可走时返回 `DecisionFeedback{Code:"UNREACHABLE"}`，调用方据此让 AI 放弃或触发终局。

谁在用它？三个场景（`round_engine.go`）：持包者去包点（自动下包前置）、炸弹掉落后的救包路径（`ScheduleBombRecovery`）、以及下包后全员冲向包点（回防/守包）。**不可达就是不可达**——不存在"隔空捡包"或"瞬移到包点"的保底（第 13 篇的 `ValidNoProgress` 会利用这一点）。

## 5. 拦截：设计有，生产没接

设计文档的拦截模型（`doc/simuMatchDesign.md#3.3`）：移动路径经过敌方可见点位时，**在移动完成前插入一次 Intercept**，交火结果决定继续走、撤退还是死亡。

实现完整躺在 `movement.go` 里，而且质量不低：

- `ScheduleInterceptCheck`（`movement.go#ScheduleInterceptCheck`）：每条边至多一个拦截检查（`interceptByTraversal` 去重）；触发概率 = `Risk/250 + Noise/500 + confidence/1000`，加上"可见 +0.2、架点 +0.1"的修正；命中则在移动窗口的 25%–75% 处安排 `ActionInterceptCheck`（优先级 60）。
- `ResolveInterceptCheck`（`movement.go#ResolveInterceptCheck`）：先把父移动的进度推进到拦截点，再生成 EncounterCandidate 开打。
- `InterruptMovementForEncounter`（`movement.go#InterruptMovementForEncounter`）：推进进度 → 清行动 → `Version++` → 进入 `Engaged`。

**但**：`ScheduleInterceptCheck` 和 `InterruptMovementForEncounter` 在生产代码里没有任何调用者（grep 全库只有测试调用），`ResolveInterceptCheck` 虽有分发分支却永远没有行动被调度进去。所以生产中的"中途遭遇"实际由另一条路径触发：`discoverEncounters`（`round_engine.go#discoverEncounters`）扫描**同节点或可见**的 T/CT 组合直接开战。拦截管线属于"单元测试全绿、生产未启用"的准死代码——第 15 篇 Q3。

## 6. 位置如何变成战报坐标

移动、击杀、下包的事件坐标都走 `event_projection.go#eventLocation`（第 13 篇详解），核心规则：

- 在节点上：节点配了 Circle/Polygon → 在该区域内**种子派生采样**；没配 → 用节点 `x/y` + 极小抖动。
- 在边上：用 `OnEdgeLocation.X/Y` 并 clamp 到合法区间。

采样种子 = `deriveSeed(roundSeed, "event_location", eventID, 来源对象ID)`（设计文档的 `LocationSeed` 概念）。同一事件在同一场比赛中永远落在同一个坐标——前端雷达图上的每个点都是可复现的。

## 本篇回顾

- 空间 = 语义图（Node/Edge/Route/Visibility），不做物理仿真，但语义真实参与结算。
- 移动 = "一段有代价的边"：耗时由 base_time × 节奏 + 体能/机动修正，clamp 防瞬移。
- 位置不变量 Node XOR Edge；`OnEdgeLocation.Progress` 表达"走到一半"。
- 寻路是有界确定性 Dijkstra；不可达返回 UNREACHABLE，无瞬移保底。
- 拦截管线实现完整但生产未接线，生产中接触由 `discoverEncounters` 触发（已知缺口）。
