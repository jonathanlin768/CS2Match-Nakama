# 13 · 回合收尾：炸弹、终局与战报投影

> 内核区的最后一篇，也是因果链的终点：炸弹怎么走完它的一生、终局怎么从状态里"读"出来、以及战报如何从已应用的 Effect 投影成前端能看的东西。
>
> 前置依赖：07（权威状态）、12（战斗脉冲）。

## 1. 炸弹状态机：七个状态，十一个门

`BombState` 的权威状态只有七个（`round_state.go#BombRuntimeStatus`）：`Carried → Dropped → Planting → Planted → Defusing → Defused / Exploded`。所有转换方法都**先验前置、违例报错**（`SIMULATION_INVARIANT_ERROR`），比如：

| 方法 | 前置条件（违例即拒绝） |
|------|----------------------|
| `StartPlant` | Carried 且调用者就是 CarrierID，finishAt > startAt |
| `CompletePlant` | Planting 且 **at == PlantFinishAt**，explodeAt > at |
| `StartDefuse` | Planted 且 finishAt ≤ ExplodeAt |
| `CompleteDefuse` | Defusing 且 at == DefuseFinishAt 且 **at ≤ ExplodeAt（允许等号！）** |
| `Pickup` | Dropped 且拾取者与炸弹**同位置** |
| `Explode` | Planted/Defusing 且 at == ExplodeAt |

两个细节直接编码了设计文档的边界规则（`doc/simuMatchDesign.md#2.7`）：

- **`CompleteDefuse` 允许 `at == ExplodeAt`**：拆包完成与爆炸同秒 → 判 CT 赢（"等号判给 CT"）。
- **`CompletePlant` 允许踩线**：下包完成时刻 == 回合截止时刻 → 下包成功（"先结算同秒事件；下包者存活则下包成功"）。

## 2. 行动层：下包、拆包、救包

`bomb.go` 把状态机包装成行动。下包链：

```text
CanAttemptPlant（存活唯一持包者、不忙、Timeline ≤ RoundDeadline、
                节点是 Plant 用途且匹配 Site、控制权不是 CT/Contested）
→ StartPlantAction（扣 UtilityPlantCover 预算；
   时长 = BasePlantTime − 掩护 − (Discipline−50)/100，clamp 到 Min/MaxPlantTime；
   BeginExclusiveAction(Planting) → Bomb.StartPlant → 入队，任一步失败逐层回滚）
→ ResolvePlantComplete（恰好 1 名有效执行者、时刻匹配、
   炸弹状态/行动 ID/位置全对 → Planted；
   写 BombDeadline = explodeAt；Phase = PostPlant；安排爆炸行动（优先级 50））
```

拆包链多一道"T 能否阻止"的判断（`CanDenyDefuse`）：任一存活 T 在 `DefuseFinishAt` 之前能到达炸弹节点，拆包尝试直接拒绝——"T 还活着且赶得过来"时，CT 不能无风险下钳。拆包时长受拆弹钳影响（HasKit 减半），并消耗 `UtilityDefuseCover` 掩护预算。

救包链（`ScheduleBombRecovery`）：炸弹 Dropped 后，空闲 T 寻路到掉落点（`FindBoundedPath`），行动时长 = 移动 + 拾取（`BasePickupTime` 修正后 clamp）；炸弹在 CT 控制点 → `SITE_CONTEST_REQUIRED`（先打架再捡）。`ResolveBombPickup` 到点时瞬移到炸弹位置并 `Pickup`。

**打断闭环**：这些"进行中"的状态（Planting/Defusing）遇到第 12 篇的 `interruptBombActionForPlayer`——被打中或死亡 → `InterruptPlant/InterruptDefuse` 回退状态 + 生成 `PLANT_INTERRUPT/DEFUSE_INTERRUPT` 事件。状态机 + 行动版本 + Effect 打断，三套机制咬合成"下包会被打断"的完整语义。

## 3. 同秒边界：优先级表的实战

第 8 篇的优先级表在炸弹场景下有三场经典对决（`bomb_test.go` 都有对应测试）：

| 同秒场景 | 结算顺序 | 结果 |
|---------|---------|------|
| 击杀持包者 vs 下包完成 | 脉冲(100) → 掉包(80) → 下包完成(70) | 下包失败，BOMB_DROP |
| 击杀拆包者 vs 拆包完成 | 脉冲(100) 先 | 拆包失败 |
| 拆包完成 vs 炸弹爆炸 | 拆包(60) 先于爆炸(50) | CT 赢 |

## 4. 终局：纯函数读状态

`terminal.go#EvaluateRoundTerminal` 是**纯函数**——只读状态、不写任何东西（测试断言了这一点）。判定顺序（`terminal.go#EvaluateRoundTerminal`）：

```text
炸弹已拆除            → CT 胜  bomb_defused
炸弹已爆炸            → T 胜   bomb_exploded
（未下包阶段）
  T 全灭              → CT 胜  elimination（炸弹 Dropped 时原因码加 T_ELIMINATED_BOMB_DROPPED）
  CT 全灭             → T 胜   elimination
  Timeline ≥ 回合截止 → CT 胜  timeout
  NoProgressEligible 且 ValidNoProgress → CT 胜 no_progress_timeout
（已下包阶段）
  CT 全灭 且本批无拆包事件 → T 胜 bomb_secured
```

两个容易问"为什么"的规则：

1. **下包后 T 全灭不结束回合**——拆包判定仍然进行（设计文档："T 全灭但包已下时，仍执行拆包判定"）。只有 CT 也全灭（且没有同秒拆包成功）才是 `bomb_secured`。
2. **`no_progress_timeout` 是"最后手段"**，不是普通终局。它有独立的资格门槛，见下节。

终局产生后，`enterRoundEnd`（`round_engine.go#enterRoundEnd`）取消所有行动、清空队列、生成 `ROUND_END` 事件，然后跑 `ValidateTerminalInvariants`（`terminal.go#ValidateTerminalInvariants`）：逐选手核对生死一致（`Alive == (HP>0)`）、死者无行动、持包者与炸弹一致；炸弹按状态核对生命周期（已下包必须有 `BOMB_PLANT` 事件、已拆除/爆炸必须有对应事件）；事件流有序且不超前。**任何不一致都返回错误，绝不修复**——不变量被破坏说明上游写坏了，掩盖只会埋雷。

## 5. NoProgress：卡死时的确定性恢复

"双方都找不到对方、T 也永远下不了包"怎么办？不能随便判 timeout（时间可能还没到），也不能无限空转。`noop.go` 实现了一套**恢复周期**机制：

**第一步：指纹检测**。`StateFingerprint`（`noop.go#StateFingerprint`）对时间、资源、位置、炸弹、控制权、调度队列、事件等做 SHA-256（各维度排序保证 map 遍历顺序无关）。主循环每批后 `ObserveStateProgress` 比较指纹：没变化 → `RecordNoOp`（`NoOpCount++`）；有变化且来自恢复行动自身 → 保留周期；有变化且来自其他行动 → `resetRecoveryCycle` 清空一切。

**第二步：触发恢复**。连续 NoOp 达到 `MaxNoOpTransitions` → 创建恢复周期（`CycleID = stableObjectID("recovery", seed, "no_progress_recovery", RecoveryOrdinal)`，序号只增不回滚）。`ScheduleNoProgressRecovery`（`noop.go#ScheduleNoProgressRecovery`）按情况给一次**确定性**恢复行动：炸弹掉落 → 救包；持包 → 去最近可达包点（到了就 `StartPlantAction`，没到就移动）。

**第三步：判定资格**。`ValidNoProgress`（`noop.go#ValidNoProgress`）只描述业务状态：未下包、T 仍有存活、没有待决的移动/拾取/下包行动、包点存在，且（Carried → 持包者不可达任何包点；Dropped → 炸弹不可达且无人能到炸弹）。**只有 `NoProgressEligible=true` 且 `ValidNoProgress` 成立**，终局纯函数才判 `no_progress_timeout`。

区分度在于：**普通批次哪怕状态恰好"不可达"，也不会直接终局**——必须走完"连续无进展 → 恢复尝试 → 仍不可恢复"的完整证明链。配置坏了、图断了、调度器超限，返回的是结构化 `SIMULATION_ERROR`，绝不伪装成 `no_progress_timeout`。

> ⚠️ **设计 vs 现实提示**：`CompleteNoProgressRecovery`（恢复行动完成后的"成功/失败"分类）在生产代码中没有调用者——生产里 `NoProgressEligible` 只能通过恢复行动**调度失败**的分支置位。也就是说，"恢复尝试成功了但仍不可达 → 正式判 no_progress_timeout"这条路径当前生产不可达（Review 指南 Q4，第 15 篇）。

## 6. 战报投影：从 Effect 到前端 JSON

回合结束后，`round_projection.go#ProjectRoundResult` 把权威状态投影成 DTO：

1. **先 `ClampAndValidate` 再投影**——投影前做最后一次体检；
2. `Terminal` 非空才写 `Winner/WinReason`——终局是投影的输入，不是投影的产物；
3. `projectBombState` 做**兼容投影**：`Planting → Carried`、`Defusing → Planted`（老客户端枚举没有"进行中"状态，只能映射到最近的公开状态）；
4. 玩家状态、控制权快照（`KnownByT/CT`）按排序投影——map 顺序不能进 JSON。

事件投影（`event_projection.go`）有两条硬规则：

- **`ProjectReasonRecord` 拦截隐藏字段**（`event_projection.go#hiddenStateField`）：StateChanges 的字段名里含 `intent / actionqueue / actualcontrol / hidden` 一律拒绝——AI 的内心戏永远进不了战报；
- **`snapshotForEvent` 只含公开状态**：排序后的玩家投影、控制权认知、炸弹投影、比分——没有调度器、没有行动队列。

### 事件位置：语义采样

`eventLocation`（`event_projection.go#eventLocation`）决定每个事件在地图上的坐标：节点配了 `Circle` → 在圆内种子派生采样（角度 `stableUnit(seed,"angle")×2π`、半径 `√stableUnit(seed,"radius")×R`）；`Polygon` → 包围盒 + 拒绝采样（16 次尝试 + 射线法，全败回退节点中心）；没配 → 节点 `x/y` 加极小抖动；在边上 → `OnEdgeLocation.X/Y`。采样种子 = `deriveSeed(roundSeed, "event_location", eventID, 来源对象ID)`——**同一事件的坐标永远一致**，前端雷达图因此可复现。

### 事件排序键

`sortEvents`（`engine.go#sortEvents`）：`Timestamp 升序 → sortPriority 降序（回退到事件类型优先级：KILL(5) < BOMB_PLANT(6) < BOMB_DEFUSE(7) < BOMB_EXPLODE(8) < ROUND_END(9)，同秒 KILL 先展示）→ sortActionType → sortMinActorID → SourceActionID → SourceEffectID → EventID → EventType → Message`。前端拿到的就是这条稳定序。

### 可解释报告

`BuildExplainableReport(round)` / `BuildMatchExplainableReport(rounds)` 从整场事件与 ReasonRecord 聚合出 KeyEvents（关键击杀/下包/拆包/转折点）、StrategySummary（双方战术一览）、LossReasons（败因：哪类事件后局势崩了）、WinFactors（胜因）。这是"结果可解释"原则的最后一块拼图——前端第一版只展示 KILL，但整条审计链已经在 JSON 里。

## 本篇回顾

- 炸弹七状态、十一个带前置校验的转换门；同秒边界靠优先级表裁决（等号判 CT）。
- 终局是纯函数读出来的：拆除 > 爆炸 > 淘汰 > 超时 > 无进展；下包后 T 全灭不结束。
- 终局后跑完整不变量校验，只报错不修复。
- NoProgress = 指纹检测 + 一次确定性恢复 + 资格判定；配置错误绝不伪装成该终局。
- 投影三条铁律：先体检再投影、隐藏字段进不了战报、事件坐标种子派生可复现。
