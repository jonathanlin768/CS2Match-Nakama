# 07 · 权威状态与不变量

> 这篇讲引擎的"唯一真值"——`RoundState`。理解它，后面所有 resolver（行动、战斗、炸弹、投影）都只是"读它、验证它、改它"的不同姿势。
>
> 前置依赖：06（回合主循环）。

## 1. 为什么要区分"权威状态"和"对外投影"

引擎内部状态（`RoundState`）和返回给前端的 DTO（`RoundResult`）是**两套结构**。原因有三：

1. **内部字段不适合公开**：调度器、行动队列、情报记录、恢复周期都是实现细节，暴露出去既无意义又是信息泄漏（比如把 AI 的真实意图发给客户端，就给了作弊者上帝视角）。
2. **公开格式要稳定**：前端契约（JSON 字段）需要向后兼容，内部结构则可以自由重构。
3. **投影是单向的**：`RoundResult` 只能从 `RoundState` 投影出来，**永远不能写回去**。这是"权威性"的操作定义：只有一个地方可以改状态。

`model.go` 里 DTO 的每个字段基本都能在 `round_state.go` 里找到投影源，读代码时两边对照是最高效的方式。

## 2. RoundState：回合的一切

`round_state.go#RoundState` 的公开字段（还有一组私有字段持有配置快照的只读引用：constants、mapEdges、routes、routeTemplates、scenarios、mapTags、encounterModifiers、visibility、weaponSpecs）：

```go
type RoundState struct {
    RoundNumber  int
    Seed         int64        // 本回合派生种子（第 5 篇见过派生公式）
    Phase        RoundPhase   // 主导活动投影（第 6 篇）
    Timeline     int          // 唯一递增时钟
    RoundDeadline int         // 下包前有效：回合结束绝对时刻
    BombDeadline  int         // 下包后有效：爆炸绝对时刻

    TeamTID / TeamCTID / TeamAID / TeamBID string
    ScoreByTeam map[string]int

    Plan     RoundPlan                  // 战术模板/角色/路线/持包人
    Players  map[string]*RoundPlayerState
    Bomb     BombState                  // 独立实体
    Nodes    map[string]*NodeRuntimeState
    Intel    map[string]*TeamIntel      // side → 情报
    ActiveEngagements map[string]*EncounterState

    Scheduler *ActionScheduler
    MomentumT / MomentumCT int          // 团队气势（±100）
    Utility  map[string]*TeamUtilityState  // 道具预算

    DecisionCount / RotationCount / TransitionCount / NoOpCount int
    NoProgressEligible bool
    RecoveryOrdinal int
    RecoveryAttempt NoProgressRecoveryState

    Events   []*GameEvent
    Terminal *RoundTerminal
    PhaseHistory []RoundPhase
}
```

看字段布局就能读出设计意图：

- **时间只有三个数**：`Timeline`（现在几点）+ 两个 deadline。回合倒计时和炸弹倒计时都是**投影值**（`RoundDeadline - Timeline`），不需要到处手动减秒——这是设计文档明确要求的方式（`doc/simuMatchDesign.md#2.3`）。
- **Bomb 是独立实体**，不是某个玩家的附属字段（见下文）。
- **Momentum 是队伍级的**，而 HP/Stamina/Focus 是选手级的——两层资源模型的边界一目了然。
- **NoOp/Recovery 相关字段占了半屏**，可见"防卡死"是引擎的一等公民。

## 3. 选手状态：Profile 与运行时分离

`round_state.go#RoundPlayerState` 同样贯彻了"静态与动态分离"：

```go
type RoundPlayerState struct {
    Profile PlayerProfile   // 静态档案：ID、名字、角色标签、15 项属性
    TeamID  string
    Side    string
    Weapon  WeaponLoadout   // 武器配置（本回合装备）

    Alive     bool
    HP        int           // 0..MaxHP
    Stamina   int
    Focus     int
    Suppressed bool         // 被压制标记
    Momentum  int

    Location  PlayerLocation  // Node XOR Edge
    Posture   CombatPosture
    Intent    Intent          // 战术意图
    Action    PlayerActionState  // 当前行动 + 版本
    EngagementID string

    HasBomb bool
    Kills / Deaths / Damage int
}
```

设计文档的约束在这里逐条落地（`doc/simuMatchDesign.md#2.4`）：**引擎从不修改 `Profile`**（静态档案只读），运行时变化全部发生在 `Alive/HP/Stamina/Focus/Location/…` 这些运行时字段上。这把"选手是谁"和"选手现在怎么样"干净地切开了。

## 4. 三个"认知分离"：引擎最精妙的设计

### 4.1 炸弹：独立权威实体

`BombState`（`round_state.go#BombState`）有自己的生命周期方法：`Drop/StartPlant/CompletePlant/InterruptPlant/StartDefuse/CompleteDefuse/InterruptDefuse/Pickup/Explode`。**每个方法先校验状态机前置条件，违例返回 `SIMULATION_INVARIANT_ERROR`，绝不悄悄迁移**。

比如 `Pickup`（`round_state.go#Pickup`）要求：状态是 `Dropped`、拾取者与炸弹同位置。炸弹在边上掉落时，位置是 `OnEdgeLocation`（第 9 篇），拾取者必须走到同一条边——"隔空取物"在状态机层面就不可能发生。完整状态机流转是第 13 篇的主角。

### 4.2 控制权：Actual vs Known

`NodeRuntimeState`（`round_state.go#NodeRuntimeState`）每个节点存两个层次：

```go
type NodeRuntimeState struct {
    Node           MapNode      // 配置引用
    ActualControl  ControlState // 引擎真实控制权（真相）
    KnownControl   map[string]KnownControlState  // side → 该方认知
    UpdatedAt      int
}
```

- `ActualControl`：引擎知道的真相（比如 B 点实际是 T 控制的）。
- `KnownControl`：**每一方各自以为的控制权**，带 `Status/UpdatedAt/ObservedBy/ExpiresAt`。

AI 决策只能读 `KnownControl`（本方），**不能读 `ActualControl`**——这是设计文档 2.1 的硬性信息边界。认知的更新走 `ResolveContest`（冲突结算后：写真相 + 按观察者写认知 + 设 TTL 过期时间），过期走 `DecayKnownControl`（时间到 → 降级回 `Unknown`、清空观察者）。你站在 B 洞"以为"控制着 B 点，30 秒没人看之后，这个认知就过期了——情报会腐烂，这是真实 CS 的一部分。

### 4.3 情报：TeamIntel（当前是"空转"状态）

`round_state.go#TeamIntel` 结构齐全（`Records/KnownEnemies/KnownControl/SoundCues/BombIntel`），`intel.go` 里 `RecordIntel`、置信度分层、TTL 衰减也都实现了——但 Review 发现**生产路径没有调用 `RecordIntel`**：决策视图里的情报恒为空，AI 目前只靠权威状态 + `KnownControl` 做决策。这是第 15 篇"设计 vs 现实"的重点条目（Q2）。

## 5. 初始化：NewRoundState 干了什么

`round_state.go#NewRoundState` 把 `RoundInput` + `RoundPlan` 变成回合的"第一帧"：

| 项目 | 初始值 |
|------|--------|
| Phase | `OpeningDeploy` |
| RoundDeadline | `RoundTimeLimit`（90s） |
| Utility 预算 | 双方各 `UtilityBudget` 常量值 |
| 节点控制权 | 按配置 `DefaultSide` 给 T/CT 初始优势，其余 `Unknown` |
| 选手 | 每队强制恰好 5 人、出生点存在；HP/Stamina/Focus = 对应 `Max*` 常量 |
| 持包人 | 强制存活 T 且存在，否则 `INVALID_OPENING_PLAN`；`Bomb = {Carried, CarrierID, Location}` |
| RecoveryAttempt | `NotAttempted` |

收尾必跑一次 `ClampAndValidate`（见下）——**第一帧状态也必须合法**。

## 6. ClampAndValidate：每批之后的不变量闸门

`round_state.go#ClampAndValidate` 是引擎的"体检清单"，在任何状态可能被改坏的地方都会被调用。它校验的不变量（每条都能在 `round_invariant_test.go` 找到对应测试）：

- **数值边界**：Momentum ±100；HP/Stamina/Focus 各自钳位到配置范围；`Timeline` 不越 `MaxRoundTimeline`。
- **生死一致**：`HP == 0 ⟺ Alive == false`；死亡玩家不能还持有 `CurrentActionID`（死者不停车就报错）。
- **位置 XOR**：`PlayerLocation.Valid()`——`NodeID` 与 `Edge` 必须恰有一个非空（`action.go#PlayerLocation.Valid`，异或逻辑）。这是"Node XOR Edge"不变量在代码里的精确表达。
- **炸弹一致**：`HasBomb` 必须与 `Bomb.CarrierID` + 状态吻合；非 `Carried/Planting` 状态时 `CarrierID` 必须为空；持包者恰好一人。
- **终局闭合**：`Phase == RoundEnd` 时 `Terminal` 必须存在。

这个函数的价值在于**失败立刻报错，而不是修复**：不变量被破坏说明上游 resolver 写坏了状态，静默修复只会把 bug 埋得更深。

## 7. 一个贯穿全专栏的阅读技巧

读引擎代码时永远问三个问题：

1. **谁拥有这个状态？**（只有一个所有者：`RoundState` 及其子结构）
2. **谁被允许改它？**（resolver 产出 Effect/结果，应用层统一落地——第 8、12 篇）
3. **改动后谁负责体检？**（`ClampAndValidate` / `ValidateTerminalInvariants`）

把这三个问题套在任何函数上，你就能快速判断它属于哪一层、有没有越权。

## 本篇回顾

- `RoundState` 是唯一权威真值；DTO 只能投影，不能写回。
- 选手静态档案（Profile）与运行时状态分离，引擎永不改档案。
- 三个认知分离：炸弹独立实体、Actual vs Known 控制权、TeamIntel（生产目前空转）。
- `NewRoundState` 构造合法的"第一帧"；`ClampAndValidate` 是每批之后的不变量闸门，只报错不修复。
